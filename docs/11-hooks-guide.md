# 10-훅-활용-가이드

지금까지 Skills, MCP Servers, Plugins & Marketplace까지 다루면서, Grok Build의 확장 기능 중 상당 부분을 살펴보았습니다.

이제 마지막으로 다룰 주제가 있습니다.

바로 **Hooks**입니다.

Hooks는 Grok Build의 확장 기능 중에서 **가장 강력하면서 동시에 가장 위험한** 기능입니다.  
잘 사용하면 개발 생산성과 품질을 크게 끌어올릴 수 있지만, 잘못 사용하면 오히려 개발 흐름을 방해하고, 심지어 보안 사고를 일으킬 수도 있습니다.

이 문서는 Hooks를 **안전하고 실질적으로** 활용하는 데 집중합니다.

---

## 1. Hooks란 무엇인가?

### Hook의 본질

Hook은 **특정 이벤트가 발생했을 때, 자동으로 무언가를 실행**하게 만드는 기능입니다.

쉽게 말해 “이런 일이 생기면, Grok이 알아서 뭐 좀 해줘”라고 설정하는 것입니다.

주요 이벤트 예시:
- 파일이 저장될 때
- Git 커밋을 하기 직전 (`pre-commit`)
- Git 커밋을 푸시하기 직전 (`pre-push`)
- Grok Build 세션이 시작될 때
- 빌드가 성공하거나 실패했을 때

### Hooks vs 다른 확장 기능

| 확장 기능     | 주된 목적             | 실행 주체     | 자동화 정도 | 위험도 |
|---------------|-----------------------|---------------|-------------|--------|
| **Skills**    | 반복 작업의 일관성    | Grok (요청 시) | 낮음        | 낮음   |
| **MCP**       | 외부 도구 연동        | Grok (요청 시) | 중간        | 중간   |
| **Plugins**   | 확장 기능 묶음/배포   | -             | -           | 중간   |
| **Hooks**     | 이벤트 기반 자동 실행 | 시스템 (자동) | 높음        | **높음** |

Hooks는 “사용자가 요청할 때”가 아니라, **특정 사건이 발생하는 순간 자동으로 실행**된다는 점에서 다른 확장 기능과 근본적으로 다릅니다.

---

## 2. Hooks의 위험성과 왜 신중해야 하는가?

Hooks는 강력한 만큼, 잘못 사용하면 큰 문제를 일으킬 수 있습니다. 실제로 많은 팀이 Hooks를 도입했다가 오히려 생산성이 떨어지는 경험을 합니다.

### Hooks가 위험한 이유

**1. 자동으로 실행된다는 점**
- 사용자가 의도하지 않았는데도 코드가 실행되거나, 파일이 수정될 수 있음
- 실수 한 번으로 커밋 자체를 막아버릴 수 있음

**2. 개발 흐름을 방해할 수 있음**
- pre-commit hook이 10초 이상 걸리면, 매번 커밋할 때마다 기다려야 함
- 팀원들이 “커밋이 너무 귀찮다”며 hook을 우회하는 나쁜 습관이 생길 수 있음

**3. 보안 위험**
- pre-commit hook이 민감한 정보를 외부로 전송할 수 있음
- 악의적이거나 잘못 작성된 hook이 시스템 명령을 실행할 수 있음

**4. 유지보수 비용**
- 프로젝트가 커질수록 hook이 복잡해지고, 관리하기 어려워짐
- 한 사람이 만든 hook이 다른 사람의 개발을 방해하는 경우가 많음

### Hooks를 도입하기 전에 반드시 물어야 할 질문

- 이 Hook이 **정말 필요한가?** (Skill이나 MCP로 충분하지 않은가?)
- 이 Hook이 실패했을 때, 개발자들이 **불편함을 감수할 가치**가 있는가?
- 이 Hook을 **모든 팀원이 이해하고 유지보수**할 수 있는가?

이 질문에 자신 있게 답할 수 없다면, Hook을 만들기 전에 한 번 더 고민하는 것이 좋습니다.

## 3. 주요 Hook 이벤트

Grok Build에서 지원하는 주요 Hook 이벤트는 다음과 같습니다.

### 자주 사용되는 Hook 이벤트

| Hook 이벤트          | 설명                              | 사용 빈도 | 위험도 | 추천 대상 |
|----------------------|-----------------------------------|-----------|--------|-----------|
| `pre-commit`         | 커밋하기 직전 실행                | ★★★★★     | 높음   | 대부분의 팀 |
| `pre-push`           | 푸시하기 직전 실행                | ★★★☆☆     | 중간   | 중요한 브랜치 보호 |
| `post-commit`        | 커밋이 완료된 후 실행             | ★★☆☆☆     | 낮음   | 알림, 로깅 |
| `session-start`      | Grok 세션이 시작될 때             | ★★★☆☆     | 낮음   | 환경 초기화 |
| `session-end`        | Grok 세션이 종료될 때             | ★★☆☆☆     | 낮음   | 정리 작업 |
| `file-save`          | 파일이 저장될 때 (일부 환경)      | ★★☆☆☆     | 중간   | 실시간 검사 |

### 가장 많이 쓰이는 Hook: pre-commit

실무에서 가장 많이, 그리고 가장 조심스럽게 사용되는 Hook은 `pre-commit`입니다.

**pre-commit Hook으로 할 수 있는 일**:
- 코드 스타일 검사 (ESLint, Prettier, Black 등)
- 타입 검사 (TypeScript, mypy 등)
- 테스트 실행 (일부 또는 전체)
- 보안 검사 (secret scanning, 의존성 취약점 검사)
- 커밋 메시지 검사

## 4. 기본 Hook 만들기

### Hook 파일 위치

Hooks는 보통 프로젝트 루트의 `.grok/hooks/` 폴더 안에 정의합니다.

예시 구조:
```bash
.grok/hooks/
├── pre-commit.json
├── pre-push.json
└── session-start.json
```

### 간단한 pre-commit Hook 예시

```json
{
  "name": "pre-commit-lint-and-typecheck",
  "description": "커밋 전에 lint와 typecheck를 실행합니다.",
  "events": ["pre-commit"],
  "commands": [
    {
      "name": "lint",
      "command": "pnpm lint",
      "failOnError": true,
      "timeout": 30000
    },
    {
      "name": "typecheck",
      "command": "pnpm typecheck",
      "failOnError": true,
      "timeout": 60000
    }
  ]
}
```

### Hook 작성 시 중요한 옵션

- `failOnError`: 명령이 실패하면 커밋을 막을지 여부 (true 추천)
- `timeout`: 명령 실행 최대 시간 (너무 길면 개발 방해)
- `runInBackground`: 백그라운드로 실행할지 여부

## 5. 실전 Hook 패턴 (상세 예시)

이 섹션에서는 실제로 많은 팀이 사용하거나, 사용을 고려하는 구체적인 Hook 패턴들을 다룹니다.

### 5.1 pre-commit: Lint + Typecheck + Test (가장 흔한 조합)

```json
{
  "name": "pre-commit-quality-check",
  "description": "커밋 전에 코드 품질을 검사합니다.",
  "events": ["pre-commit"],
  "commands": [
    {
      "name": "lint",
      "command": "pnpm lint",
      "failOnError": true,
      "timeout": 30000
    },
    {
      "name": "typecheck",
      "command": "pnpm typecheck",
      "failOnError": true,
      "timeout": 60000
    },
    {
      "name": "test",
      "command": "pnpm test -- --run --passWithNoTests",
      "failOnError": true,
      "timeout": 120000
    }
  ]
}
```

**주의점**:
- test 명령은 전체 테스트가 아닌 **변경된 파일 관련 테스트만** 실행하는 것이 좋습니다 (예: `vitest run --changed`).
- 전체 테스트를 pre-commit에 넣으면 커밋할 때마다 너무 오래 걸려서 팀원들이 hook을 우회하게 됩니다.

### 5.2 pre-commit: Secret Scanning

민감한 정보(API 키, 비밀번호 등)가 코드에 포함되는 것을 막는 Hook입니다.

```json
{
  "name": "pre-commit-secret-scan",
  "description": "커밋 전에 민감 정보 유출을 검사합니다.",
  "events": ["pre-commit"],
  "commands": [
    {
      "name": "secret-scan",
      "command": "npx secretlint \"**/*\"",
      "failOnError": true,
      "timeout": 30000
    }
  ]
}
```

### 5.3 pre-push: Branch Protection

중요한 브랜치(main, develop)에 직접 푸시하는 것을 막는 Hook입니다.

```json
{
  "name": "pre-push-branch-protection",
  "description": "중요 브랜치에 직접 푸시하는 것을 방지합니다.",
  "events": ["pre-push"],
  "commands": [
    {
      "name": "check-branch",
      "command": "bash -c 'if [[ $(git branch --show-current) =~ ^(main|develop)$ ]]; then echo \"직접 푸시가 금지된 브랜치입니다.\"; exit 1; fi'",
      "failOnError": true
    }
  ]
}
```

### 5.4 session-start: 환경 초기화

Grok 세션이 시작될 때 자동으로 필요한 환경을 설정하는 Hook입니다.

예: `.env` 파일 확인, 필요한 Docker 컨테이너 실행, 데이터베이스 마이그레이션 상태 확인 등.

## 6. Hook과 다른 확장 기능의 연동

Hooks는 다른 확장 기능과 함께 사용했을 때 진가가 발휘됩니다.

### 6.1 Hook + Skill

**가장 추천하는 조합**

- Hook이 먼저 검사 (lint, typecheck, secret scan 등)
- 실패하면 Skill이 실패 원인을 분석하고 수정 제안을 해줌

**예시 흐름**:
1. pre-commit Hook이 lint 실패를 감지
2. Grok이 “lint가 실패했습니다. Skill을 사용해서 자동으로 수정해드릴까요?”라고 제안
3. 사용자가 승인하면 Skill이 코드를 수정

이렇게 하면 단순히 “막는” Hook이 아니라 “도와주는” Hook이 됩니다.

### 6.2 Hook + MCP

- pre-commit 시점에 DB 마이그레이션 상태를 확인하는 MCP를 호출
- 변경된 파일에 따라 필요한 테스트 데이터가 있는지 MCP로 확인

### 6.3 Hook + Plugin

팀에서 자주 사용하는 Hook들을 Plugin 안에 넣어서 배포하면, 일관된 품질 검사를 강제할 수 있습니다.

예: `team-quality-plugin` 안에
- pre-commit (lint + typecheck + secret scan)
- pre-push (branch protection)

## 7. Hook 관리와 팀 내 도입 전략

### Hook 관리 추천 방식

- Hook 설정 파일은 `.grok/hooks/` 안에 모아서 관리
- Hook은 **가능한 한 간결하게** 유지 (복잡한 로직은 Skill이나 별도 스크립트로 분리)
- Hook 실패 시 “왜 실패했는지”를 개발자가 쉽게 이해할 수 있게 로그를 남김

### 팀에서 Hook을 도입하는 전략

**1단계: 선택적 도입**
- 처음에는 모든 사람에게 강제하지 말고, 원하는 사람만 Hook을 사용하게 함
- 피드백을 받아가며 Hook을 다듬음

**2단계: 표준 Hook 정의**
- 팀에서 합의된 Hook을 Plugin으로 묶어서 배포
- “이 Hook을 쓰면 이런 장점이 있다”는 것을 문서화

**3단계: 강제 도입 (선택)**
- 팀 문화가 충분히 성숙하고, Hook이 안정적일 때만 강제하는 것을 고려

### 언제 Hook을 도입하지 않는 것이 더 나을까?

- 팀 규모가 작고, 코드 리뷰 문화가 잘 되어 있을 때
- 프로젝트가 아직 불안정해서 자주 구조가 바뀔 때
- Hook을 관리할 수 있는 사람이 명확하지 않을 때

## 8. 보안 위험과 실패 사례

### 실제로 발생할 수 있는 위험

**1. Hook이 민감 정보를 외부로 전송**
- pre-commit hook이 코드에서 API 키를 찾아서 외부 서버로 보내는 경우

**2. Hook이 시스템 명령을 악용**
- 잘못 작성된 Hook이 `rm -rf` 같은 위험한 명령을 실행할 수 있음 (특히 `runInBackground` 옵션 사용 시)

**3. Hook이 무한 루프를 유발**
- Hook이 파일을 수정하고, 그 수정이 다시 Hook을 트리거하는 경우

**4. Hook이 개발 속도를 극도로 저하**
- pre-commit이 3분 이상 걸려서, 팀원들이 `--no-verify`로 커밋을 우회하는 문화가 생김

### 안전한 Hook 작성 원칙

- Hook은 **가능한 한 읽기 작업** 위주로 작성
- 파일을 수정하는 Hook은 신중하게 검토
- `timeout`을 적절히 설정하여 무한 대기 방지
- Hook 스크립트는 **최소 권한**으로 실행
- 중요한 Hook은 팀 전체 리뷰를 거침

## 9. Best Practices & Anti-patterns

### Best Practices (잘 만드는 법)

**1. Hook은 최대한 가볍고 빠르게**
- pre-commit은 10~15초 이내에 끝나는 것이 이상적입니다.
- 무거운 작업(전체 테스트 실행, 큰 데이터베이스 조회 등)은 Hook이 아닌 CI/CD나 별도 스크립트로 분리하세요.

**2. 실패 시 명확한 메시지 제공**
- Hook이 실패했을 때 “무엇이 잘못되었는지”를 개발자가 한눈에 알 수 있게 메시지를 작성하세요.
- 단순히 “실패했습니다”가 아니라 “lint 오류가 있습니다. pnpm lint를 실행해보세요.”처럼 구체적으로.

**3. 선택적 실행 고려**
- 모든 파일에 대해 Hook을 실행할 필요는 없습니다.
- 변경된 파일만 검사하는 방식(`lint-staged` 등)을 적극 활용하세요.

**4. 팀 전체 리뷰 필수**
- 중요한 Hook(pre-commit, pre-push)은 최소한 팀 리더나 아키텍트가 리뷰해야 합니다.
- 특히 파일을 수정하거나 외부 명령을 실행하는 Hook은 더 신중하게 검토.

**5. Hook은 Plugin으로 관리**
- Hook 설정도 Plugin 안에 포함해서 배포하면, 팀 전체가 일관된 Hook을 쉽게 사용할 수 있습니다.

### Anti-patterns (피해야 할 패턴)

**1. God Hook**
- pre-commit 하나에 lint, typecheck, test, security scan, DB migration 확인까지 다 넣는 경우.
- → Hook이 너무 느려지고, 실패 원인을 파악하기 어려워짐.

**2. 무조건 강제하는 Hook**
- 팀 문화가 아직 성숙하지 않았는데 Hook을 강제로 적용하면, 팀원들이 `--no-verify`를 남발하게 됩니다.
- → 오히려 품질이 떨어지는 역효과.

**3. 파일을 함부로 수정하는 Hook**
- pre-commit에서 자동으로 코드 포맷을 수정하고 커밋까지 해버리는 경우.
- → Git 히스토리가 지저분해지고, 팀원들이 혼란스러워함.

**4. 외부 서비스에 의존하는 Hook**
- pre-commit에서 외부 API를 호출하는 경우 (네트워크 지연, API 다운 시 개발 중단).
- → 가능한 한 로컬에서 해결할 수 있는 작업으로 제한.

**5. 문서화되지 않은 Hook**
- Hook이 왜 있는지, 어떤 규칙을 검사하는지 설명이 없는 경우.
- → 새로운 팀원이 들어왔을 때 유지보수가 매우 어려워짐.

## 10. Hook 디버깅과 테스트 방법

### Hook이 예상대로 동작하지 않을 때

1. **Hook이 실행되었는지 확인**
   - Grok Build 하단이나 로그에서 Hook 실행 메시지가 나오는지 확인.
   - 실행되지 않았다면 이벤트 이름이 정확한지 확인 (`pre-commit` vs `pre_push` 등).

2. **명령어가 실제로 실행되는지 테스트**
   - Hook에 들어간 명령어를 터미널에서 직접 실행해보기.
   - 예: `pnpm lint`가 실제로 실패하는지 확인.

3. **timeout 문제 확인**
   - timeout이 너무 짧게 설정되어 있으면 명령이 중간에 강제 종료될 수 있음.

4. **권한 문제**
   - Hook 스크립트가 실행할 수 있는 권한이 있는지 확인 (특히 Docker, DB 접속 등).

### Hook 테스트 방법

- 작은 변경사항을 만들어서 Hook을 여러 번 트리거해보기.
- “이 Hook이 실패해야 하는 상황”을 일부러 만들어서 테스트.
- 팀원 1~2명에게 실제로 사용하게 하고 피드백 받기.

## 공식 명령어 & 고급 기능 (참고)

이 가이드에서는 실전 사용에 초점을 맞췄지만, 아래 공식 기능들도 알아두면 도움이 됩니다.

### Hook 이벤트 상세

Grok Build는 여러 종류의 Hook 이벤트를 지원합니다. 각 이벤트의 특성과 사용 목적이 다릅니다.

| 이벤트 이름            | 설명                                      | Blocking 가능? | 주요 사용 사례 |
|------------------------|-------------------------------------------|------------------|----------------|
| `SessionStart`         | Grok 세션이 시작될 때                     | No               | 환경 초기화, 비밀 정보 로드 |
| `SessionEnd`           | Grok 세션이 종료될 때                     | No               | 정리 작업, 로그 기록 |
| `UserPromptSubmit`     | 사용자가 프롬프트를 입력했을 때           | No               | 입력 검증, 자동 태깅 |
| `PreToolUse`           | Grok이 도구를 실행하기 직전               | **Yes**          | 위험한 명령 차단, 보안 검사 |
| `PostToolUse`          | Grok이 도구 실행을 완료한 직후            | No               | 실행 결과 로깅, 알림 전송 |

**특히 중요한 이벤트: `PreToolUse`**

`PreToolUse`는 **Blocking이 가능**한 이벤트입니다. 즉, 조건에 따라 Grok이 특정 도구를 실행하는 것을 **막을 수** 있습니다.

예: `rm -rf /` 같은 위험한 명령을 자동으로 차단하는 Hook을 만들 수 있습니다.

### Trust 시스템 (프로젝트 Hook)

프로젝트 폴더 안에 Hook을 만들면 (`<project>/.grok/hooks/`), Grok은 보안상의 이유로 **기본적으로 신뢰(trust)하지 않습니다**.

처음 해당 프로젝트를 열 때, Grok이 "이 프로젝트의 Hook을 신뢰하시겠습니까?"라고 물어보거나, 수동으로 신뢰를 설정해야 합니다.

**신뢰 설정 방법**:
- TUI에서 `Ctrl + L` → Hooks 탭 → `t` 키로 trust
- 또는 `/hooks trust` 명령어 사용

**주의**: 신뢰하지 않은 프로젝트의 Hook은 실행되지 않습니다. 보안상 중요한 기능이니, 신뢰할 수 있는 프로젝트에서만 Hook을 사용하는 것이 좋습니다.

### `/hooks` 관련 명령어

```bash
/hooks
/hooks trust
/hooks list
```

- `/hooks` : Hook 관리 모달 열기
- `/hooks trust` : 현재 프로젝트의 Hook을 신뢰
- `/hooks list` : 로드된 Hook 목록 확인

---

이 섹션은 참고용으로 작성되었습니다. Hook을 만들 때는 `PreToolUse` 이벤트와 Trust 시스템을 특히 신경 써주세요.

## 배경 지식: 이 기능이 왜 이렇게 동작하는가

> **참고**: 이 섹션은 Grok 공식 문서에 명시된 설계 의도를 그대로 설명한 것이 아닙니다.  
> 실제 동작 방식과 관찰, 그리고 논리적 해석을 바탕으로 작성한 **참고용 설명**입니다.  
> xAI에서 공식적으로 발표한 설계 철학이 아니라는 점을 참고해 주세요.

Hooks 시스템이 현재와 같은 형태로 제공되는 배경과 특징을 정리했습니다.

### 1. 왜 Hook 이벤트가 PreToolUse, PostToolUse 등으로 나뉘나?

Grok이 도구를 실행하는 과정을 크게 세 단계로 나눌 수 있습니다:

- **실행 전 (PreToolUse)**: 도구가 실행되기 직전 — 여기서 차단(Blocking)이 가능
- **실행 후 (PostToolUse)**: 도구 실행이 끝난 직후 — 결과 로깅, 알림 등에 적합
- **세션 시작/종료 (SessionStart / SessionEnd)**: 세션의 생명주기와 관련된 작업

이렇게 이벤트를 세분화한 덕분에, 보안이 중요한 환경에서는 `PreToolUse`를 사용해 위험한 명령을 실행하기 전에 막을 수 있고, 일반적인 환경에서는 `PostToolUse`로 로깅이나 알림을 처리하는 등 유연하게 활용할 수 있습니다.

### 2. 왜 프로젝트 Hook은 Trust(신뢰)를 받아야 하나?

프로젝트 폴더 안에 Hook을 만들으면, 그 Hook은 **자동으로 실행**될 수 있는 강력한 권한을 가지게 됩니다.  
만약 신뢰하지 않은 프로젝트의 Hook을 그대로 실행하면, 악성 Hook이 파일을 삭제하거나 정보를 외부로 유출할 위험이 있습니다.

그래서 Grok은 보안상의 이유로 **프로젝트 Hook은 기본적으로 trust(신뢰)되지 않도록** 하고, 사용자가 직접 신뢰 여부를 결정하게 합니다.

### 3. 왜 Hook을 프로젝트 단위로 관리하나?

프로젝트마다 다른 품질 기준, 보안 정책, 워크플로가 있을 수 있습니다.  
따라서 Hook도 프로젝트별로 관리하는 것이 자연스럽고, 유지보수하기도 쉽습니다.  
Plugin 안에 Hook을 포함하면, 팀 전체가 동일한 Hook을 쉽게 공유할 수 있다는 장점도 있습니다.

## 디버깅 체크리스트

Hook이 제대로 동작하지 않을 때, 아래 순서대로 확인해보세요.

### Hook이 실행되지 않을 때

1. **Hook이 로드되었는지 확인**
   - TUI에서 `Ctrl + L` → Hooks 탭에서 Hook이 보이는지 확인하세요.
   - 보이지 않으면 파일 위치(`.grok/hooks/`)나 JSON 문법을 확인하세요.

2. **프로젝트 Hook의 경우 Trust 여부 확인**
   - 프로젝트 Hook은 기본적으로 trust되지 않습니다.
   - `/hooks trust` 명령어를 실행했는지, 또는 TUI에서 trust를 했는지 확인하세요.

3. **이벤트 이름이 정확한지 확인**
   - `pre-commit`이 아니라 `PreToolUse`처럼 정확한 이벤트 이름을 사용해야 합니다.
   - 대소문자도 중요합니다.

### Hook이 너무 자주 실행되거나 느릴 때

1. **timeout 값이 적절한지 확인**
   - Hook에 `timeout`이 너무 길게 설정되어 있으면, 실패해도 오랫동안 기다리게 됩니다.

2. **Hook 스크립트 자체가 느린지 확인**
   - Hook 안에 들어간 shell 명령이나 스크립트가 느리면, 전체 Hook 실행이 느려집니다.
   - 가능하면 가벼운 명령으로 유지하세요.

### Hook이 에러를 낼 때

1. **Hook 로그 확인**
   - Hook 실행 결과에 에러 메시지가 있는지 확인하세요.
   - Grok은 Hook 실행 결과를 대화 중에 알려주는 경우가 많습니다.

2. **권한 문제 확인**
   - Hook 스크립트가 실행할 수 있는 권한이 있는지 확인 (특히 Docker, DB 접속 등).

3. **JSON 문법 오류**
   - Hook 파일(`.grok/hooks/*.json`)의 JSON 문법이 올바른지 확인하세요. (콤마, 괄호, 따옴표 등)

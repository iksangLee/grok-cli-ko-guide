# 11-프로젝트 규칙 (AGENTS.md)

Grok Build를 프로젝트에서 사용할 때, 매번 같은 규칙을 설명하는 것은 매우 비효율적입니다.  
예를 들어 “이 프로젝트는 TypeScript를 사용하고, 함수형 컴포넌트를 선호하며, ESLint 규칙을 따라야 해” 같은 지시를 매 세션마다 반복해야 한다면 금방 피곤해집니다.

이럴 때 사용하는 것이 바로 **프로젝트 규칙**입니다.

---

## 프로젝트 규칙이란 무엇인가?

**프로젝트 규칙**은 특정 프로젝트(또는 디렉토리)에서 Grok이 항상 따라야 할 규칙을 미리 정해두는 기능입니다.

프로젝트 루트(또는 하위 폴더)에 특정 이름의 Markdown 파일을 만들어두면, Grok이 그 파일의 내용을 **시스템 프롬프트에 자동으로 추가**합니다.

이렇게 하면:
- 매번 같은 설명을 반복할 필요가 없음
- 팀 전체가 동일한 코딩 컨벤션과 규칙을 공유할 수 있음
- 프로젝트의 아키텍처 방향, 스타일 가이드, 빌드 규칙 등을 영구적으로 지정할 수 있음

### 실제로 어떤 규칙을 넣을 수 있나?

- “이 프로젝트는 TypeScript를 사용합니다. any 타입은 최대한 피하세요.”
- “React 컴포넌트는 함수형으로만 작성하세요.”
- “커밋 메시지는 Conventional Commits 형식을 따르세요.”
- “테스트는 Vitest로 작성하고, 파일명은 `*.test.ts`로 하세요.”
- “API 변경이 있을 때는 반드시 문서도 함께 수정하세요.”

이런 규칙들을 한 번만 적어두면, Grok이 그 프로젝트 안에서는 항상 이 규칙을 기억하고 따릅니다.

---

## 지원하는 파일 이름

Grok은 아래 파일들을 순서대로 찾아서 사용합니다:

1. `Agents.md`
2. `Claude.md`
3. `AGENT.md`
4. `AGENTS.md`

가장 먼저 발견된 파일을 사용합니다.  
`Claude.md`는 Claude Code와의 호환성을 위해 지원됩니다.

**실전 추천**: 대부분의 경우 `AGENTS.md`를 사용하는 것이 일반적입니다.

---

## 발견(Discovery) 방식과 우선순위

Grok은 프로젝트 규칙을 다음과 같은 순서로 찾아서 로드합니다 (위쪽이 우선순위가 높음):

1. **Global 규칙** — `~/.grok/AGENTS.md` (모든 프로젝트에 적용)
2. **저장소(Root) 규칙** — Git 저장소 루트부터 현재 디렉토리까지 모든 `AGENTS.md`
3. **현재 디렉토리 전용** — Git 저장소가 아닌 경우, 현재 작업 디렉토리의 `AGENTS.md`

### 예시

프로젝트 구조가 다음과 같다고 가정해보겠습니다:

```
~/projects/my-app/
├── AGENTS.md                    ← "Use TypeScript. Follow ESLint."
├── src/
│   ├── AGENTS.md                ← "Prefer functional components."
│   └── components/
│       └── AGENTS.md            ← "Use CSS modules for styling."
└── ...
```

이 상태에서 `~/projects/my-app/src/components/` 폴더에서 Grok을 실행하면, Grok은 아래 3개의 규칙 파일을 **모두 로드**합니다:

1. `~/projects/my-app/AGENTS.md`
2. `~/projects/my-app/src/AGENTS.md`
3. `~/projects/my-app/src/components/AGENTS.md`

**더 깊은 디렉토리에 있는 파일일수록 우선순위가 높습니다.**

## 좋은 프로젝트 규칙 작성법 (Best Practices)

좋은 `AGENTS.md`를 작성하려면 아래 원칙을 지키는 것이 중요합니다.

### 1. 구체적으로 작성하라

**나쁜 예:**
```
이 프로젝트는 좋은 코드를 작성하세요.
```

**좋은 예:**
```
이 프로젝트는 TypeScript를 사용합니다.
- any 타입은 최대한 피하고, unknown을 우선적으로 사용하세요.
- interface보다는 type alias를 선호합니다.
- 함수의 반환 타입은 명시적으로 작성하세요.
```

### 2. 예시를 포함하라

규칙만 나열하지 말고, **좋은 예시와 나쁜 예시**를 함께 넣으면 Grok이 훨씬 잘 이해합니다.

예:
```
## 컴포넌트 작성 규칙

### 좋은 예
```tsx
const UserProfile = ({ user }: { user: User }) => {
  return <div>{user.name}</div>;
};
```

### 나쁜 예
```tsx
const UserProfile = (props) => {
  return <div>{props.user.name}</div>;
};
```
- props에 타입을 지정하지 않음
- any가 암묵적으로 사용될 수 있음
```

### 3. 프로젝트의 현실을 반영하라

- 실제로 지키고 있는 규칙만 적으세요.
- 이상적인 규칙을 적었다가 실제 코드가 다르면 Grok이 혼란스러워합니다.

### 4. 계층을 잘 활용하라

- 루트 `AGENTS.md`: 전체 프로젝트의 큰 방향 (아키텍처, 주요 기술 스택)
- `src/AGENTS.md`: 프론트엔드/백엔드 공통 규칙
- `src/components/AGENTS.md`: UI 컴포넌트 작성 규칙

더 구체적인 규칙일수록 하위 폴더에 작성하는 것이 좋습니다.

## 실전에서 자주 사용하는 AGENTS.md 예시

### 예시 1: React + TypeScript 팀

```markdown
# AGENTS.md

## 기술 스택
- React 18 + TypeScript
- 상태 관리: Zustand
- 스타일: Tailwind CSS + CSS Modules
- 테스트: Vitest + Testing Library

## 컴포넌트 작성 규칙
- 함수형 컴포넌트만 사용 (클래스 컴포넌트 금지)
- props는 interface로 정의
- 컴포넌트는 최대한 작게 유지 (단일 책임 원칙)

## 코드 스타일
- Prettier + ESLint 규칙을 반드시 따름
- any 타입 사용 시 반드시 주석으로 이유 작성
- 함수형 컴포넌트의 props는 별도 interface로 분리
```

### 예시 2: 백엔드 (Node.js + NestJS)

```markdown
# AGENTS.md

## 기술 스택
- NestJS + TypeScript
- 데이터베이스: PostgreSQL + Prisma
- 인증: JWT + Passport

## API 개발 규칙
- 모든 Controller는 DTO를 사용해야 함
- Service는 비즈니스 로직만 담당
- Repository 패턴을 사용

## 에러 처리
- 모든 에러는 HttpException을 상속받은 커스텀 에러로 처리
- 에러 메시지는 사용자에게 노출되지 않도록 주의
```

### 예시 3: 간단한 개인 프로젝트

```markdown
# AGENTS.md

- 이 프로젝트는 빠른 프로토타이핑을 위한 실험 프로젝트입니다.
- 타입은 대략적으로만 작성해도 괜찮습니다.
- 테스트 코드는 작성하지 않아도 됩니다.
- 커밋 메시지는 자유롭게 작성해도 됩니다.
```

## Claude Code와의 호환성

`Claude.md` 파일도 지원합니다.

- Claude Code를 사용하다가 Grok Build로 넘어온 경우, 기존에 사용하던 `Claude.md`를 그대로 활용할 수 있습니다.
- Grok은 `Claude.md`를 `AGENTS.md`와 동일하게 인식합니다.

**추천**: 가능하면 `AGENTS.md`로 통일하는 것이 좋지만, Claude Code와 병행해서 사용해야 한다면 `Claude.md`를 사용해도 무방합니다.

## 규칙이 제대로 적용되지 않을 때

### 흔한 문제와 해결 방법

**1. 규칙이 전혀 적용되지 않는다**
- 파일 이름이 정확한지 확인 (`AGENTS.md`가 맞는지)
- 파일이 Git에 ignore되어 있지 않은지 확인
- Grok을 재시작하거나 `/reload` 명령어를 사용해보기

**2. 상위 폴더의 규칙만 적용되고 하위 폴더 규칙은 무시된다**
- 더 깊은 폴더의 규칙이 우선순위가 높습니다.
- 파일이 제대로 인식되고 있는지 `grok inspect`로 확인해보세요.

**3. 규칙이 너무 길어서 무시되는 것 같다**
- AGENTS.md가 너무 길면(수천 줄) Grok이 모두 읽지 못할 수 있습니다.
- 핵심 규칙만 간결하게 작성하는 것이 오히려 효과적입니다.

**4. 특정 규칙만 적용되지 않는다**
- 규칙이 너무 모호하거나 추상적이면 Grok이 이해하기 어렵습니다.
- 구체적인 예시를 추가해보세요.

## AGENTS.md와 Skill의 차이점 + 함께 쓰는 전략

AGENTS.md와 Skill은 비슷해 보이지만, 목적과 사용 방식이 다릅니다.

### 비교

| 항목              | AGENTS.md                          | Skill                              |
|-------------------|------------------------------------|------------------------------------|
| 적용 범위         | 프로젝트 전체 (또는 폴더)          | 특정 작업/상황에만 활성화          |
| 활성화 방식       | 항상 적용                          | Grok이 관련성을 판단해서 호출      |
| 내용의 성격       | 프로젝트의 큰 방향, 철학, 규칙     | 구체적인 작업 절차, 패턴           |
| 업데이트 빈도     | 비교적 안정적                      | 자주 추가/수정됨                   |
| 공유 범위         | Git으로 공유 (팀)                  | Skill 파일 자체를 공유             |

### 함께 쓰는 전략 (추천)

**AGENTS.md**는 프로젝트의 **큰 틀**을 담당하게 하고,

**Skill**은 특정 작업의 **세부 절차**를 담당하게 하는 것이 가장 효과적입니다.

**예시 조합**:

- **AGENTS.md**:
  - "이 프로젝트는 React + TypeScript를 사용합니다."
  - "컴포넌트는 함수형으로만 작성합니다."
  - "상태 관리는 Zustand를 사용합니다."

- **Skill: `component-boilerplate`**:
  - 함수형 컴포넌트 + TypeScript + JSDoc + Storybook 파일까지 한 번에 생성하는 절차

- **Skill: `zustand-store`**:
  - Zustand 스토어 생성 시 따르는 팀의 표준 패턴을 미리 정의

이렇게 하면 AGENTS.md는 전체 방향을 잡아주고, Skill은 실제 작업을 빠르고 일관되게 도와줍니다.

## 팀 규모에 따른 프로젝트 규칙 관리 방법

### 1. 개인 프로젝트 (1인)

- 간단한 `AGENTS.md` 하나로 충분
- 규칙을 자주 바꿔도 부담이 적음
- "빠른 프로토타이핑" 모드에서는 규칙을 최소화하는 것도 좋음

### 2. 소규모 팀 (3~8명)

- 루트에 **공식 AGENTS.md** 하나를 두는 것을 추천
- 필요한 경우 하위 폴더에 보조 규칙 추가
- Plugin으로 묶어서 팀 전체가 쉽게 설치할 수 있게 관리

### 3. 중대형 팀 / 회사

- **계층 구조**를 적극 활용
  - 최상위: 전체 아키텍처 방향
  - 도메인별: 각 팀의 규칙
  - 기술 스택별: React, Backend 등
- Plugin + Marketplace를 활용해서 표준화
- AGENTS.md 변경 시 팀 리뷰 필수
- 오래된 규칙은 주기적으로 정리 (죽은 규칙이 쌓이지 않게)

## Best Practices & Anti-patterns

### Best Practices

- **핵심만 간결하게** 작성하라 (너무 길면 효과가 떨어짐)
- **예시를 적극 활용**하라 (문장보다 코드 예시가 훨씬 효과적)
- **실제로 지키는 규칙만** 적어라 (이상적인 규칙은 독이 됨)
- **계층을 잘 활용**하라 (루트는 방향, 하위는 세부)
- **Skill과 함께 사용**하라 (AGENTS.md는 방향, Skill은 절차)
- **Plugin으로 관리**하라 (팀 규모가 커질수록)

### Anti-patterns

- **God AGENTS.md**: 모든 것을 한 파일에 다 넣으려는 경우 (수천 줄)
- **추상적인 규칙**: "좋은 코드를 작성하세요", "깔끔하게 작성하세요" 같은 모호한 표현
- **죽은 규칙**: 더 이상 지키지 않는 규칙을 그대로 방치
- **과도한 계층**: 너무 많은 하위 AGENTS.md로 인해 규칙이 충돌하거나 혼란스러운 경우
- **문서 없는 규칙**: AGENTS.md가 있지만, 왜 이런 규칙인지 설명이 전혀 없는 경우

## 전체 가이드 마무리

`11-프로젝트-규칙.md`를 모두 읽었다면, 이제 Grok Build에서 **프로젝트의 목소리를 영구적으로 남기는 방법**을 배운 것입니다.

### 핵심 요약

- `AGENTS.md`는 **프로젝트의 기억**입니다.
- 더 깊은 폴더일수록 우선순위가 높습니다.
- 구체적이고, 예시가 풍부할수록 효과가 좋습니다.
- Skill과 함께 사용하면 훨씬 강력해집니다.
- 팀 규모가 커질수록 Plugin + Marketplace를 적극 활용하세요.

### 추천하는 다음 단계

이제 Grok Build의 주요 확장 기능들을 모두 살펴보았습니다.

- **Skill**로 개인/작업 단위의 규칙을 만들고
- **MCP**로 외부 도구를 연결하고
- **AGENTS.md**로 프로젝트의 방향을 정하고
- **Plugin**으로 팀 전체에 배포하고
- **Hook**으로 자동화를 걸고

이 조합을 상황에 맞게 잘 사용하면, Grok Build를 단순한 코딩 도구가 아닌 **프로젝트 전용 AI 페어 프로그래머**로 만들 수 있습니다.

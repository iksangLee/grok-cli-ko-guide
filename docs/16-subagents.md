# 15-하위 에이전트 (Subagents)

Grok Build를 사용하다 보면, 하나의 대화에서 너무 많은 일을 동시에 처리하려고 할 때가 있습니다.

예를 들어:
- 코드베이스를 전체적으로 조사하면서
- 동시에 특정 모듈을 리팩터링하고
- 테스트도 작성하고
- 문서도 정리해야 한다면...

이 모든 것을 하나의 세션에서 하려고 하면, 컨텍스트가 금방 부족해지고, Grok도 혼란스러워할 수 있습니다.

이런 문제를 해결하기 위해 Grok Build가 제공하는 기능이 바로 **Subagents**(하위 에이전트)입니다.

---

## Subagents와 Personas란 무엇인가?

### Subagents의 개념

**Subagent**는 **메인 에이전트(부모)**가 특정 작업을 **독립적인 하위 에이전트(자식)**에게 위임하는 기능입니다.

각 Subagent는:
- **자신만의 독립적인 컨텍스트 창**을 가집니다. (메인 세션의 컨텍스트를 소비하지 않음)
- 필요에 따라 **부모 세션의 대화 기록**을 일부 상속받을 수 있습니다 (`fork_context`)
- **특정 역할(페르소나)**을 부여받을 수 있습니다.
- **사용할 수 있는 도구의 범위**를 제한할 수 있습니다 (capability mode).

### Personas란?

**Persona**는 Subagent에게 부여하는 **성격, 말투, 사고방식**입니다.

예를 들어:
- "신중하고 분석적인 리서처"
- "빠르고 실용적인 구현자"
- "철저한 코드 리뷰어"

이런 페르소나를 지정하면, Subagent가 그에 맞는 스타일로 작업을 수행합니다.

---

## Subagents 비활성화

Subagents는 기본적으로 **활성화**되어 있습니다.

필요하다면 비활성화할 수 있습니다.

### 환경 변수로 비활성화

```bash
export GROK_SUBAGENTS=0
```

### config.toml에서 비활성화

```toml
# ~/.grok/config.toml
[subagents]
enabled = false
```

## Subagents가 어떻게 동작하는가?

### task 도구

Subagent를 생성하는 주된 방법은 `task` 도구를 사용하는 것입니다.

Grok이 작업을 하다가 “이 부분은 별도의 에이전트에게 맡기는 게 좋겠다”고 판단하면, 자동으로 `task` 도구를 호출합니다.

### Subagent가 가지는 특징

1. **독립적인 컨텍스트**
   - 메인 세션의 컨텍스트를 거의 사용하지 않습니다.
   - 긴 작업을 병렬로 처리하기에 매우 유리합니다.

2. **fork_context (선택적 상속)**
   - `fork_context: true`로 설정하면, 부모 세션의 대화 기록을 일부 가져올 수 있습니다.
   - `fork_context: false`이면 완전히 독립적인 세션으로 시작합니다.

3. **capability_mode (도구 사용 범위)**
   - `general-purpose`: 모든 도구 사용 가능 (기본)
   - `explore`: 읽기 전용 (조사 전용, 파일 수정/명령 실행 불가)
   - `plan`: 계획 수립 전용

4. **persona (성격 부여)**
   - Subagent의 말투, 사고방식, 접근 태도를 지정할 수 있습니다.

## Built-in Agent Types

Grok Build는 기본적으로 세 가지 유형의 Subagent를 제공합니다.

### 1. general-purpose (기본)

- **설명**: 가장 일반적인 에이전트. 모든 도구를 사용할 수 있습니다.
- **용도**: 구현, 리팩터링, 테스트 작성, 디버깅 등 거의 모든 작업

### 2. explore (조사 전용)

- **설명**: 읽기 전용 에이전트. 파일을 읽고, 검색하고, 조사할 수는 있지만 수정하거나 명령을 실행할 수는 없습니다.
- **용도**: 코드베이스 조사, 문서 분석, 기술 스택 파악, 버그 원인 찾기 등

### 3. plan (계획 전용)

- **설명**: 코드베이스를 탐색하고, 구조화된 구현 계획을 작성하는 데 특화된 에이전트.
- **용도**: 큰 리팩터링이나 기능 추가 전에 계획을 먼저 세우고 싶을 때

## Built-in Personas (내장 페르소나)

Grok Build는 Subagent에게 부여할 수 있는 기본 페르소나를 제공합니다.

### 1. general-purpose (기본 페르소나)
- **설명**: 가장 일반적인 페르소나. 특별한 성격 없이 중립적으로 작업을 수행합니다.
- **용도**: 대부분의 작업에 적합
- **특징**: 균형 잡힌 판단, 유연한 대응

### 2. explorer (탐험가 페르소나)
- **설명**: 호기심 많고 철저한 조사자 스타일
- **용도**: 코드베이스 조사, 기술 스택 분석, 문서 탐색
- **특징**: 꼼꼼한 조사, 많은 질문, 다양한 관점 제시

### 3. implementer (구현자 페르소나)
- **설명**: 실행력 있고 실용적인 구현자 스타일
- **용도**: 코드 작성, 리팩터링, 기능 구현
- **특징**: 빠른 실행, 실용적인 해결책, "일단 해보자" 태도

### 4. reviewer (리뷰어 페르소나)
- **설명**: 비판적이고 신중한 코드 리뷰어 스타일
- **용도**: 코드 리뷰, 버그 찾기, 품질 검사
- **특징**: 잠재적 문제 지적, 개선 제안, 보안/성능 관점 강조

### 5. planner (계획자 페르소나)
- **설명**: 체계적이고 논리적인 계획자 스타일
- **용도**: 프로젝트 계획 수립, 아키텍처 설계, 단계별 로드맵 작성
- **특징**: 구조화된 사고, 단계별 분해, 리스크 분석

### 6. critic (비평가 페르소나)
- **설명**: 날카롭고 솔직한 비평가 스타일
- **용도**: 설계 검토, 아이디어 비판, 대안 제시
- **특징**: 단점 지적, 대안 제안, "왜 이게 최선인가?" 질문

## `task` 도구 실제 사용법

Subagent를 생성하는 주요 방법은 `task` 도구를 호출하는 것입니다.

### 기본 호출 형식

```json
{
  "name": "task",
  "arguments": {
    "subagent_type": "general-purpose",
    "description": "이 작업을 설명하는 내용",
    "prompt": "하위 에이전트에게 전달할 구체적인 지시",
    "fork_context": true,
    "persona": "implementer"
  }
}
```

### 실제 사용 예시

**예시 1: 코드베이스 조사 (explore 타입)**

```
이 프로젝트의 인증 관련 코드를 조사해줘. 
특히 JWT 처리 방식과 에러 처리 로직을 중점으로.
```

→ Grok이 자동으로 `task` 도구를 호출해서 `explore` 타입 Subagent를 생성

**예시 2: 특정 모듈 구현 (implementer 타입)**

```
PaymentService.ts 파일을 리팩터링해줘.
- 에러 처리를 일관되게
- 로깅을 추가
- 타입 안전성을 높여
```

→ `implementer` 페르소나를 가진 Subagent에게 위임

**예시 3: 계획 수립 (plan 타입)**

```
이 프로젝트에 사용자 알림 시스템을 추가하려고 해.
어떻게 접근하면 좋을지 단계별 계획을 세워줘.
```

→ `plan` 타입 Subagent가 구조화된 계획을 작성

## Subagent와 메인 세션 간의 결과 전달

### 결과 전달 방식

Subagent가 작업을 완료하면, 그 결과는 **요약 형태**로 메인 세션에 전달됩니다.

- Subagent의 전체 대화 기록이 그대로 전달되는 것은 아님
- 중요한 결론, 생성된 코드, 발견된 문제 등이 요약되어 전달
- 필요하다면 Subagent의 세션 ID를 받아서 직접 확인할 수도 있음

### fork_context의 활용

- `fork_context: true`: 부모 세션의 대화 기록을 일부 가져와서 Subagent가 맥락을 이해할 수 있게 함
- `fork_context: false`: 완전히 독립적인 세션으로 시작 (컨텍스트 오염 방지)

**추천**:
- 조사/분석 작업 → `fork_context: true`
- 독립적인 구현 작업 → `fork_context: false`

## Subagent 활용 전략

### 언제 Subagent를 사용하는 것이 좋을까?

**1. 병렬 작업이 필요할 때**
- 여러 모듈을 동시에 리팩터링
- 여러 파일을 동시에 분석

**2. 컨텍스트를 보호하고 싶을 때**
- 메인 세션에서 큰 그림을 유지하면서, 세부 작업은 Subagent에게 위임

**3. 전문화된 역할을 부여하고 싶을 때**
- "조사만 잘하는 에이전트", "구현만 잘하는 에이전트" 등

**4. 장시간 작업을 백그라운드에서 처리하고 싶을 때**

### Subagent 활용 팁

- **너무 작은 작업은 Subagent로 위임하지 마세요.** (오버헤드가 더 큼)
- **명확한 지시를 주세요.** Subagent에게도 명확한 목표와 성공 기준을 전달해야 합니다.
- **결과를 검토하세요.** Subagent의 결과는 자동으로 메인 세션에 반영되지 않으므로, 잘 검토한 후 적용하세요.

## Subagent와 다른 확장 기능의 연동

Subagent는 다른 확장 기능과 함께 사용했을 때 더 강력해집니다.

### Subagent + Skill

- Subagent가 특정 작업을 수행하는 동안, Skill을 통해 그 작업의 **표준 절차**를 따르게 할 수 있습니다.
- 예: `explore` 타입 Subagent에게 "코드베이스 조사"를 맡기면서, `unit-test-generation` Skill을 통해 테스트 관련 파일을 찾게 함.

### Subagent + MCP

- Subagent가 데이터베이스나 GitHub 같은 외부 도구를 사용할 때, MCP 서버를 통해 안전하고 통제된 방식으로 접근할 수 있습니다.
- 예: `explore` 타입 Subagent가 DB MCP를 사용해서 스키마를 조사.

### Subagent + Hooks

- Subagent가 파일을 수정할 때, Hook을 통해 자동으로 lint나 test를 실행하게 할 수 있습니다.
- 예: Subagent가 코드를 수정한 후, pre-commit Hook이 자동으로 품질 검사를 수행.

### Subagent + Plugin

- 팀에서 자주 사용하는 Subagent 패턴을 Plugin으로 묶어서 배포할 수 있습니다.
- 예: "Payment Domain Investigation Plugin" 안에 explore 타입 Subagent + 관련 MCP + Skill을 포함.

## Subagent 관리와 팀 내 도입 전략

### Subagent 관리 추천

- Subagent 세션도 일반 세션처럼 `~/.grok/sessions/` 안에 저장됩니다.
- 중요한 Subagent 세션은 세션 ID를 기록해두면 나중에 `/load`로 불러올 수 있습니다.
- Subagent의 결과는 메인 세션에 요약 형태로 전달되므로, 필요하다면 Subagent 세션 ID를 받아서 직접 확인하는 것이 좋습니다.

### 팀 내 도입 전략

**1단계: 작은 작업부터 시작**
- 처음에는 "조사" 작업(`explore` 타입)부터 Subagent에게 위임해보세요.
- 메인 세션이 너무 길어지지 않도록 보호하는 용도로 사용.

**2단계: 표준 Subagent 패턴 만들기**
- 팀에서 자주 위임하는 작업(예: "리팩터링", "테스트 작성", "보안 검사")에 대한 표준 Subagent 패턴을 정의.
- Plugin으로 묶어서 팀 전체가 쉽게 사용할 수 있게 배포.

**3단계: 복잡한 작업 위임**
- 큰 리팩터링이나 기능 추가 시, `plan` 타입 Subagent로 먼저 계획을 세우게 하고, `implementer` 타입으로 구현을 위임하는 식으로 활용.

### 주의할 점

- Subagent를 너무 많이 생성하면 관리가 어려워집니다. (보통 2~4개 정도가 적당)
- Subagent의 결과는 **자동으로 메인 세션에 반영되지 않으므로**, 항상 결과를 검토한 후 적용해야 합니다.
- `fork_context: true`를 남용하면 메인 세션의 컨텍스트가 Subagent로 퍼져서 오히려 비효율적일 수 있습니다.

## Best Practices & Anti-patterns

### Best Practices

- **작업을 명확하게 분리하라**: Subagent에게 넘길 작업은 "조사", "구현", "리뷰"처럼 명확히 구분되는 것이 좋습니다.
- **페르소나를 적극 활용하라**: `explorer`, `implementer`, `reviewer` 등 역할을 명확히 지정하면 더 좋은 결과를 얻습니다.
- **결과를 검토하라**: Subagent의 결과는 요약이므로, 중요한 변경은 직접 확인하세요.
- **Plugin으로 관리하라**: 팀에서 자주 사용하는 Subagent 패턴은 Plugin으로 묶어서 배포하세요.

### Anti-patterns

- **God Subagent**: 하나의 Subagent에게 너무 많은 일을 맡기는 경우.
- **과도한 fork_context**: 모든 Subagent에게 부모 컨텍스트를 다 넘겨주면 컨텍스트 낭비가 발생.
- **결과 미검토**: Subagent 결과를 그대로 믿고 적용하다가 문제가 생기는 경우.
- **너무 많은 Subagent**: 한 번에 5개 이상의 Subagent를 동시에 돌리면 관리하기 어려움.

## 전체 가이드 마무리

`15-하위-에이전트.md`를 모두 읽었다면, 이제 Grok Build의 **병렬 작업** 기능을 이해한 것입니다.

### 핵심 요약

- Subagent는 **독립적인 컨텍스트**를 가진 하위 에이전트입니다.
- `task` 도구로 생성하며, `subagent_type`과 `persona`로 역할을 지정할 수 있습니다.
- `fork_context`로 부모 세션의 맥락을 선택적으로 상속받을 수 있습니다.
- Skill, MCP, Hooks, Plugin과 잘 연동하면 강력한 자동화가 가능합니다.
- 팀 규모가 커질수록 Subagent 패턴을 Plugin으로 관리하는 것이 효율적입니다.

### Subagent 추천 사용처

- 코드베이스 조사 (`explore`)
- 큰 리팩터링 전 계획 수립 (`plan`)
- 병렬 구현 작업 (`implementer`)
- 코드 품질 검사 (`reviewer`)

Subagent를 잘 활용하면, Grok Build가 **하나의 에이전트**가 아니라 **여러 명의 AI 개발팀**처럼 일할 수 있게 됩니다.

## 배경 지식: 이 기능이 왜 이렇게 동작하는가

> **참고**: 이 섹션은 Grok 공식 문서에 명시된 설계 의도를 그대로 설명한 것이 아닙니다.  
> 실제 동작 방식과 관찰, 그리고 논리적 해석을 바탕으로 작성한 **참고용 설명**입니다.  
> xAI에서 공식적으로 발표한 설계 철학이 아니라는 점을 참고해 주세요.

Subagent 시스템이 현재와 같은 형태로 동작하는 배경과 특징을 정리했습니다.

### 1. 왜 Subagent가 독립적인 컨텍스트를 가지는가?

메인 에이전트의 컨텍스트 창은 한정되어 있습니다.  
만약 모든 작업을 하나의 컨텍스트에서 처리하려고 하면, 금방 토큰이 부족해지고 중요한 정보가 압축되거나 사라질 수 있습니다.

그래서 Subagent는 **자신만의 독립적인 컨텍스트**를 가지도록 설계되었습니다.  
이렇게 하면 메인 에이전트는 큰 그림을 유지하면서, 세부 작업은 Subagent에게 위임할 수 있습니다.

### 2. 왜 persona와 capability_mode가 분리되어 있나?

- **capability_mode**: Subagent가 **무엇을 할 수 있는지**를 기술적으로 제한 (explore는 읽기만, plan은 계획만 등)
- **persona**: Subagent가 **어떻게 행동하고 말할지**에 대한 성격과 스타일을 지정

이 둘을 분리함으로써, 같은 `explore` 타입이라도 “신중하고 보수적인 조사자” persona를 적용하거나, “빠르고 광범위하게 탐색하는 조사자” persona를 적용하는 등 유연하게 활용할 수 있습니다.

### 3. 왜 fork_context 옵션이 있나?

모든 Subagent가 부모 세션의 대화 기록을 필요로 하지는 않습니다.  
때로는 완전히 독립적으로 작업하는 것이 더 좋을 때가 있고, 때로는 부모의 맥락을 어느 정도 알아야 할 때가 있습니다.

그래서 `fork_context: true/false` 옵션으로 선택할 수 있게 하여, 필요에 따라 부모 컨텍스트를 상속받을지 여부를 제어할 수 있도록 했습니다.

## 디버깅 체크리스트

Subagent가 제대로 동작하지 않을 때, 아래 순서대로 확인해보세요.

### Subagent가 생성되지 않을 때

1. **task 도구가 제대로 호출되었는지 확인**
   - Subagent를 생성하려면 `task` 도구를 사용해야 합니다.
   - 프롬프트에서 "이 작업을 Subagent에게 맡겨"라고 명확히 요청했는지 확인하세요.

2. **capability_mode가 너무 제한적인지 확인**
   - `explore` 타입은 파일을 수정하거나 shell을 실행할 수 없습니다.
   - 필요하다면 `general-purpose`로 변경해보세요.

### Subagent의 결과가 제대로 오지 않을 때

1. **fork_context 설정 확인**
   - `fork_context: false`로 설정했다면, Subagent는 부모 세션의 맥락을 전혀 모릅니다.
   - 필요한 맥락이 있다면 `fork_context: true`로 설정하세요.

2. **결과가 기대보다 간략하게 올 때**
   - Subagent는 기본적으로 작업 결과를 요약해서 전달합니다.
   - 더 자세한 내용을 보고 싶다면 Subagent가 사용한 세션 ID를 받아서 직접 `/load` 해보세요.

### Subagent가 이상한 스타일로 답변할 때

- `persona` 설정이 제대로 반영되지 않았을 가능성이 있습니다.
- persona 설명을 더 구체적으로 작성해보세요 (예: "신중하고 보수적인 코드 리뷰어" vs "그냥 리뷰어").

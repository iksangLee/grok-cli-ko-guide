# 02-확장-기능-시작하기

Grok Build는 단순히 강력한 AI 코딩 어시스턴트가 아닙니다.  
더 중요한 것은 **필요에 따라 얼마든지 확장할 수 있는** 유연한 시스템을 가지고 있다는 점입니다.

이 문서는 Grok Build의 확장 기능 전체를 한눈에 이해하고,  
“내 프로젝트에는 어떤 걸 도입하면 좋을까?”를 판단할 수 있도록 도와주는 것을 목적으로 합니다.

---

## 1. Grok에는 왜 이렇게 많은 확장 기능이 있을까?

대부분의 AI 코딩 도구는 “더 똑똑한 모델 하나”를 만드는 데 집중합니다.  
Grok Build는 조금 다른 철학을 가지고 있습니다.

### Grok Build의 기본 생각

> “완벽한 AI 하나를 만드는 것보다,  
> 사용자가 필요한 도구를 직접 붙일 수 있게 하는 것이 더 강력하다.”

이런 생각 때문에 Grok Build는 다음과 같은 확장 기능을 제공합니다:

- **Skills**: 자주 반복되는 작업을 재사용 가능한 형태로 만들기
- **MCP Servers**: 외부 도구(데이터베이스, GitHub, Linear, 브라우저 등)를 AI가 직접 사용할 수 있게 연결
- **Hooks**: 코드 커밋, 파일 저장, 세션 시작/종료 등 특정 시점에 자동으로 무언가를 실행
- **Plugins**: 위의 기능들을 하나로 묶어서 팀이나 커뮤니티와 공유
- **Marketplace**: 다른 사람이 만든 플러그인을 쉽게 찾아서 설치

### 왜 이런 방식을 택했을까?

- 모든 걸 모델이 알아서 하게 하면, 모델이 커질수록 복잡해지고 통제하기 어려워집니다.
- 반대로, **필요한 기능은 외부 도구로 분리**하면 사용자가 직접 선택하고 조합할 수 있습니다.
- 프로젝트마다, 팀마다, 개인마다 필요한 것이 다르기 때문입니다.

예를 들어:
- 어떤 사람은 “Git 커밋 메시지를 자동으로 예쁘게 써주는 기능”만 필요할 수 있고,
- 어떤 팀은 “Linear 이슈와 연동해서 자동으로 작업을 추적”하는 기능이 필요할 수 있습니다.

Grok Build는 이런 다양한 요구를 **하나의 모델로 다 해결하려고 하지 않고**, 확장 시스템을 통해 열어둔 것입니다.

## 2. 5가지 확장 기능, 한눈에 비교하기

아래 표는 Grok Build의 주요 확장 기능을 목적, 난이도, 언제 쓰면 좋은지 기준으로 정리한 것입니다.

| 확장 기능          | 주요 목적                          | 난이도 | 언제 쓰면 좋은가                                      | 주의할 점                     | 대표적인 사용 예시 |
|--------------------|------------------------------------|--------|-------------------------------------------------------|-------------------------------|--------------------|
| **Skills**         | 반복 작업을 재사용 가능한 형태로 만들기 | 하     | 같은 패턴의 작업을 자주 하는 경우                     | 만들기 쉽지만, 품질 관리가 중요 | Git 커밋 메시지 자동 작성, 테스트 코드 생성 패턴 |
| **MCP Servers**    | 외부 서비스·도구를 AI가 직접 사용 | 중     | 데이터베이스, API, 브라우저, GitHub 등과 연동이 필요할 때 | 서버 설정과 권한 관리가 필요 | Postgres 조회, GitHub 이슈 생성, 파일시스템 접근 |
| **Hooks**          | 특정 이벤트(커밋, 저장 등)에 자동 실행 | 중~상 | 코드 품질 자동 검사, 보안 검사, 알림 보내기 등       | 잘못 만들면 개발 흐름을 방해할 수 있음 | pre-commit 시 lint + type check 실행 |
| **Plugins**        | 여러 기능을 하나로 묶어서 배포    | 중     | 팀 내에서 공통으로 쓰는 도구 세트를 만들고 싶을 때   | 의존성 관리와 호환성 확인 필요 | 팀용 스킬 + MCP + 훅을 한 번에 설치 |
| **Marketplace**    | 다른 사람이 만든 플러그인을 쉽게 설치 | 하     | 이미 만들어진 좋은 플러그인을 빠르게 도입하고 싶을 때 | 신뢰할 수 있는 소스인지 확인 필요 | 커뮤니티에서 만든 유용한 플러그인 설치 |

### 한 줄 요약

- **Skills**: “이 작업은 이렇게 하자”를 미리 정해두는 것
- **MCP Servers**: “Grok이 이 도구를 직접 쓸 수 있게 해주는 것”
- **Hooks**: “이런 일이 생기면 자동으로 뭐 좀 해줘”를 설정하는 것
- **Plugins**: 위의 것들을 **하나의 패키지**로 만들어 공유하는 것
- **Marketplace**: 다른 사람들이 만든 패키지를 쉽게 가져다 쓰는 것

## 3. Claude Code, Cursor 사용 경험자라면

Claude Code나 Cursor + Claude를 이미 사용해보신 분들이 Grok Build의 확장 기능을 처음 보면, 종종 이런 반응을 보입니다.

> “Claude도 이미 꽤 잘하는데, 왜 이렇게 복잡하게 확장 기능을 만들어 놓은 거지?”

이 섹션에서는 그런 분들을 위해 솔직하게 차이점을 정리했습니다.

### Claude Code / Cursor와 가장 큰 차이

| 관점                  | Claude Code / Cursor                  | Grok Build 확장 시스템                     |
|-----------------------|---------------------------------------|--------------------------------------------|
| **기본 철학**         | 강력한 모델 + 좋은 컨텍스트           | 모델 + 사용자가 직접 붙이는 도구들         |
| **도구 사용 방식**    | 모델이 내부적으로 판단해서 사용       | 명시적으로 MCP 서버를 등록해서 사용        |
| **재사용성**          | 대화마다 비슷한 지시를 반복           | Skill로 한 번 만들어두면 계속 재사용       |
| **팀 공유**           | 설정을 공유하기 어려움                | Plugins + Marketplace로 쉽게 배포 가능     |
| **자동화**            | 제한적                                | Hooks로 이벤트 기반 자동화 가능            |

### Claude Code 사용자가 느끼는 Grok의 장점

- **MCP Servers** 덕분에 Claude보다 **더 다양한 외부 도구**를 연결할 수 있습니다. (Postgres, Redis, 브라우저 제어, Linear, Notion 등)
- **Skills** 시스템으로 “이 프로젝트에서는 항상 이렇게 하자”는 규칙을 **파일로 저장**해둘 수 있습니다. 매번 설명할 필요가 없어집니다.
- **Plugins + Marketplace**를 통해 팀 전체가 같은 확장 기능을 쉽게 사용할 수 있습니다. Cursor에서는 설정 공유가 상대적으로 번거롭습니다.
- Hooks를 통해 “커밋하기 전에 무조건 테스트를 돌려” 같은 규칙을 강제할 수 있습니다.

### Claude Code 사용자가 처음에 헷갈려할 수 있는 점

1. **“그냥 자연스럽게 말하면 안 되나요?”**  
   Grok도 기본적으로는 자연스럽게 대화할 수 있습니다.  
   다만, **반복되는 작업**을 안정적으로 하고 싶다면 Skill이나 MCP를 명시적으로 설정하는 편이 훨씬 효과적입니다.

2. **권한 모델이 더 명시적이다**  
   Claude Code는 비교적 조용히 파일을 읽고 수정하는 경우가 많습니다.  
   Grok은 Tool call이 발생할 때마다 비교적 명확하게 “이걸 실행해도 될까요?”라고 물어봅니다.  
   처음에는 번거로울 수 있지만, 안전성 측면에서는 더 투명합니다.

3. **설정하는 데 시간이 더 걸린다**  
   Claude Code는 바로 시작하기 쉽습니다.  
   Grok은 처음에 MCP 서버를 등록하거나 Skill을 만드는 데 약간의 학습 비용이 있습니다.  
   대신 그 투자가 나중에는 훨씬 큰 생산성으로 돌아옵니다.

### 한 줄 조언

- Claude Code에서 **이미 충분히 만족**하고 있다면, 굳이 Grok으로 넘어올 필요는 없습니다.
- 하지만 **팀 단위로 표준을 만들고 싶다**, **다양한 외부 도구를 깊게 연동**하고 싶다, **반복 작업을 체계적으로 자동화**하고 싶다면 Grok의 확장 시스템이 더 강력한 선택지가 될 수 있습니다.

## 4. Skills — 가장 추천하는 첫걸음

Grok Build의 확장 기능 중에서 **가장 추천하는 시작점**이 Skills입니다.

### Skills란?

Skill은 “이런 상황에서는 이렇게 행동해”라는 **반복적인 작업 패턴**을 미리 정의해두는 것입니다.

한 번 Skill을 만들어두면, Grok이 그 상황을 인지했을 때 자동으로 해당 Skill을 참고하거나 제안하게 됩니다.  
매번 같은 설명을 반복할 필요가 없어집니다.

### 왜 Skills부터 시작하는 걸 추천할까?

- 만들기가 비교적 쉽습니다.
- 바로 생산성 향상을 체감할 수 있습니다.
- 실패해도 큰 위험이 없습니다.
- 나중에 MCP나 Hooks를 배울 때도 Skills와 함께 쓰면 훨씬 강력해집니다.

### 간단한 사용 예시

**예시 1: Git 커밋 메시지 자동 작성**

프로젝트에 자주 쓰는 커밋 컨벤션이 있다면, Skill로 만들어둘 수 있습니다.

- Skill 파일을 만들어 “커밋 메시지는 Conventional Commits 형식으로 작성하고, 이모지를 사용하지 마”라고 규칙을 정의
- 이후에 “이 변경사항에 대한 커밋 메시지를 작성해줘”라고 하면, Skill에 정의된 규칙을 자동으로 따름

**예시 2: 테스트 코드 작성 패턴**

특정 프로젝트에서 테스트를 항상 같은 스타일로 작성한다면:

- “테스트는 Vitest를 사용하고, describe → it → expect 순서로 작성해”
- “각 테스트는 독립적으로 실행 가능해야 해”
- 같은 지시를 매번 하지 않아도 Grok이 Skill을 참고해서 일관된 테스트 코드를 작성

Skills는 **“프로젝트의 코딩 컨벤션”**을 AI에게 가르치는 가장 가벼운 방법입니다.

## 5. MCP Servers — 강력하지만 설정이 필요한 도구

MCP Servers는 Grok Build의 확장 기능 중에서 **가장 강력하면서도 가장 많이 쓰이는** 기능입니다.

### MCP Servers란?

MCP(Model Context Protocol) 서버는 **외부의 도구나 서비스를 Grok이 직접 사용할 수 있게** 연결해주는 역할을 합니다.

예를 들어:
- 로컬 파일 시스템 접근
- PostgreSQL, MySQL 같은 데이터베이스 조회 및 조작
- GitHub, Linear, Notion, Slack 등 외부 서비스 연동
- 브라우저 제어, 터미널 명령 실행 등

Grok이 단순히 “알고 있는 지식”으로 답변하는 것이 아니라, **실제 데이터를 읽고 쓰고**, **실제 서비스를 조작**할 수 있게 됩니다.

### 언제 MCP Servers를 도입하면 좋을까?

- 프로젝트에서 자주 데이터베이스를 조회해야 할 때
- GitHub 이슈나 PR을 직접 생성/관리하고 싶을 때
- 로컬 파일을 체계적으로 탐색하면서 작업하고 싶을 때
- 팀 내부 도구(예: 사내 API, 모니터링 도구)와 연동하고 싶을 때

### 주의할 점

MCP 서버는 강력한 만큼 **설정 비용**과 **권한 관리**가 필요합니다.  
특히 데이터베이스나 외부 서비스를 연결할 때는 보안에 신경 써야 합니다.

### 간단한 사용 예시

**예시 1: 로컬 파일 시스템 MCP**

프로젝트 폴더를 MCP 서버로 등록하면, Grok이 폴더 구조를 직접 탐색하고 필요한 파일을 찾아서 읽을 수 있습니다.

**예시 2: PostgreSQL MCP**

데이터베이스 MCP 서버를 연결하면, Grok에게 “users 테이블의 최근 10개 레코드를 보여줘”라고 요청할 수 있고, 실제로 쿼리를 실행해서 결과를 받아올 수 있습니다.

MCP Servers는 “Grok이 그냥 말만 하는 AI”에서 “실제 작업을 수행할 수 있는 AI”로 바꿔주는 가장 중요한 확장 기능입니다.

## 6. Hooks — 자동화를 위한 양날의 검

Hooks는 Grok Build의 확장 기능 중에서 **가장 자동화 성격이 강한** 기능입니다.

### Hooks란?

특정 이벤트가 발생했을 때, 자동으로 무언가를 실행하게 만드는 기능입니다.

주요 이벤트 예시:
- 파일이 저장될 때
- Git 커밋을 하기 직전 (pre-commit)
- 세션이 시작되거나 종료될 때
- 빌드가 성공하거나 실패했을 때

예를 들어 “커밋하기 전에 lint와 type check를 무조건 실행”하거나, “중요한 파일이 수정되면 팀 채널에 알림을 보내”는 등의 작업을 자동화할 수 있습니다.

### 언제 Hooks를 쓰면 좋을까?

- 코드 품질을 강제로 유지하고 싶을 때 (lint, formatter, type check)
- 보안 규칙을 자동으로 검사하고 싶을 때
- 중요한 변경이 있을 때 팀에 자동으로 알림을 받고 싶을 때

### 주의할 점 (양날의 검)

Hooks는 매우 강력하지만, **잘못 만들면 개발 생산성을 크게 저해**할 수 있습니다.

- pre-commit hook이 너무 오래 걸리면 매번 커밋할 때마다 기다려야 합니다.
- 잘못된 hook이 동작하면 파일 저장이나 커밋 자체를 막아버릴 수도 있습니다.
- 보안상 위험한 명령이 hook에 들어가면 큰 문제가 될 수 있습니다.

따라서 Hooks는 **팀 내에서 충분히 논의하고, 점진적으로 도입**하는 것이 좋습니다.

### 간단한 사용 예시

**예시: pre-commit hook**

프로젝트 루트에 hook을 설정해서, 커밋하기 전에 다음을 자동 실행:

- `pnpm lint`
- `pnpm typecheck`
- 특정 파일(예: `.env`)이 수정되지 않았는지 검사

이렇게 하면 “실수로 console.log를 남기고 커밋하는 일”이나 “타입 에러가 있는 코드를 커밋하는 일”을 상당 부분 줄일 수 있습니다.

## 7. Plugins & Marketplace — 팀/커뮤니티로 확장하기

Skills, MCP, Hooks를 개별적으로 관리하는 것은 처음에는 괜찮지만, 프로젝트가 커지거나 팀 단위로 사용하게 되면 관리하기 어려워집니다.

이때 등장하는 것이 **Plugins**과 **Marketplace**입니다.

### Plugins이란?

Plugin은 여러 확장 기능을 하나로 묶은 **패키지**입니다.

예를 들어 “우리 팀용 플러그인”을 만들면 다음과 같은 것들을 한 번에 포함할 수 있습니다:

- 팀에서 공통으로 쓰는 5~6개의 Skills
- 프로젝트에서 자주 쓰는 MCP 서버 설정
- pre-commit, pre-push에 필요한 Hooks
- 팀 컨벤션을 담은 AGENTS.md 조각

이렇게 만들어두면, 새로운 팀원이 들어왔을 때 “이 플러그인 하나만 설치해”라고 하면 모든 설정이 한 번에 끝납니다.

### Marketplace란?

Marketplace는 다른 사람들이 만든 플러그인을 쉽게 찾아서 설치할 수 있게 해주는 곳입니다.

Grok Build 내에서 `Ctrl + L` → Marketplace 탭을 열면, Git 저장소로 등록된 다양한 플러그인을 검색하고 설치할 수 있습니다.

### 언제 Plugins / Marketplace를 도입하면 좋을까?

- 팀 내에서 확장 기능을 표준화하고 싶을 때
- 여러 프로젝트에서 비슷한 Skills와 MCP 설정을 반복해서 만들고 있을 때
- 커뮤니티에서 이미 만들어진 좋은 플러그인을 활용하고 싶을 때

### 간단한 사용 예시

**예시: 팀용 플러그인**

- `team-conventions`라는 플러그인을 만들어서 GitHub에 올림
- 내부에는 팀의 Skills 8개 + MCP 설정 2개 + pre-commit hook 1개가 포함
- 새로운 프로젝트를 시작할 때, Marketplace에서 `team-conventions` 플러그인을 설치하면 모든 규칙이 자동 적용

Plugins와 Marketplace는 **개인 → 팀 → 커뮤니티**로 확장 기능을 확장시켜주는 역할을 합니다.

## 8. 내 프로젝트에는 어떤 걸 도입하면 좋을까?

지금까지 여러 확장 기능을 살펴보았습니다.  
이제 중요한 질문은 “**내 상황에는 어떤 걸 도입하는 게 좋을까?**”입니다.

아래는 프로젝트 유형별 추천을 정리한 것입니다.

### 상황별 추천 가이드

| 프로젝트 유형              | 추천 우선순위                  | 이유 |
|---------------------------|--------------------------------|------|
| **개인 프로젝트 / 학습**   | **Skills** → MCP (필요할 때)   | 가장 가볍고 바로 효과를 볼 수 있음. MCP는 필요할 때만 추가 |
| **소규모 팀 (3~8명)**      | **Skills** + **Plugins**       | 팀 컨벤션을 Skill로 만들고, Plugin으로 한 번에 배포하는 게 효과적 |
| **중대형 팀 / 회사**       | **Plugins** + **Hooks**        | 표준화와 자동화가 중요. Plugins로 규칙을 배포하고, Hooks로 강제 |
| **오픈소스 프로젝트**      | **Skills** + **Marketplace**   | 다른 기여자들이 쉽게 참여할 수 있게 Skill을 공개하고, Marketplace를 활용 |
| **스타트업 (빠른 속도 중요)** | **Skills** + **MCP** (선택)    | 빠르게 생산성을 올리면서, 필요할 때만 외부 도구 연동 |
| **보안이 매우 중요한 프로젝트** | **Hooks** (신중하게) + 최소한의 MCP | 자동 보안 검사 + 최소한의 외부 연동으로 리스크 관리 |

### 프로젝트 유형별 추천 조합

앞서 상황별 추천을 했지만, 실제로는 **프로젝트의 규모와 성격**에 따라 가장 효과적인 확장 기능 조합이 달라집니다. 아래는 현실적인 프로젝트 유형별로 추천하는 조합을 정리한 것입니다.

#### 1. 1인 프로젝트 (개인 프로젝트 / 학습용)

**추천 조합**: **Skills + Memory** (가볍게 시작)

**이유**:
- 혼자서 작업하므로 복잡한 팀 표준은 필요 없음
- 반복되는 작업 패턴을 Skill로 만들면 생산성이 크게 올라감
- Memory로 프로젝트에서 발견한 패턴이나 결정을 축적하면 장기적으로 큰 도움이 됨

**시작 추천 순서**:
1. Skills (필요한 작업부터 하나씩)
2. Memory (패턴이 쌓이기 시작하면)
3. MCP (필요한 도구 하나씩 추가)

---

#### 2. 소규모 팀 (3~8명)

**추천 조합**: **Skills + Plugins + AGENTS.md**

**이유**:
- 팀 컨벤션을 통일해야 하는 단계
- Plugin 하나로 여러 Skill과 MCP 설정을 한 번에 배포할 수 있어서 관리 비용이 낮음
- AGENTS.md로 큰 방향을 정하고, Skill로 세부 절차를 정의하는 조합이 효과적

**시작 추천 순서**:
1. AGENTS.md (팀 방향성 먼저 정하기)
2. Skills (팀 표준 Skill 만들기)
3. Plugins (배포용 Plugin 만들기)
4. MCP (필요한 것만 선별해서 Plugin에 포함)

---

#### 3. 중대형 팀 / 회사 (10명 이상)

**추천 조합**: **Plugins + AGENTS.md + Memory + Hooks (선별적)**

**이유**:
- 팀 규모가 크기 때문에 표준화와 자동화가 매우 중요
- Plugin으로 확장 기능을 체계적으로 관리하고 배포
- AGENTS.md로 아키텍처 방향과 기본 규칙을 명확히
- Memory로 반복되는 패턴과 결정을 축적
- Hooks는 신중하게 도입 (pre-commit 정도만 팀 전체에 강제하고, 나머지는 선택)

**시작 추천 순서**:
1. AGENTS.md (최상위 규칙)
2. Skills (팀 표준 Skill)
3. Plugins (배포 및 관리)
4. Memory (패턴 축적)
5. Hooks (선별적으로 도입)

---

#### 4. 보안이 매우 중요한 프로젝트

**추천 조합**: **Skills + AGENTS.md + 최소한의 MCP + Sandbox**

**이유**:
- MCP와 Hooks는 보안 위험이 높기 때문에 최대한 최소화
- Sandbox를 적극 활용하여 파일 시스템 접근 제한
- AGENTS.md와 Skills로 규칙을 강제하면서도 위험은 낮춤

**시작 추천 순서**:
1. AGENTS.md
2. Skills
3. Sandbox (기본 적용)
4. MCP (필요 시 읽기 전용 계정으로만 제한적으로)

---

#### 5. 오픈소스 프로젝트

**추천 조합**: **Skills + AGENTS.md + Plugins (Marketplace 공개)**

**이유**:
- 기여자들이 쉽게 참여할 수 있어야 함
- AGENTS.md로 기본 규칙을 명시
- Skills로 자주 하는 작업을 쉽게 할 수 있게 지원
- Plugin으로 만들어 Marketplace에 공개하면 기여 장벽을 낮출 수 있음

**시작 추천 순서**:
1. AGENTS.md
2. Skills
3. Plugin 제작 및 Marketplace 공개

---

이 섹션은 “내 프로젝트에는 어떤 걸 도입하면 좋을까?”를 더 구체적으로 판단할 수 있도록 돕기 위해 추가되었습니다. 프로젝트 규모와 보안 요구사항에 따라 조합을 달리 가져가는 것이 중요합니다.

## 9. 추천 학습 로드맵

Grok Build의 확장 기능을 처음 접하는 사람에게 가장 추천하는 학습 순서는 다음과 같습니다.

### 추천 순서

**1단계: Skills (1~2주)**
- 가장 쉽고, 바로 효과를 볼 수 있음
- 프로젝트의 코딩 컨벤션, 자주 하는 작업 패턴을 Skill로 만들어보기
- 이 단계에서 “Grok이 내 프로젝트를 잘 이해하게 만드는” 경험을 쌓는 것이 중요

**2단계: MCP Servers (필요할 때)**
- 실제로 외부 도구(데이터베이스, GitHub, 파일시스템 등)를 연동하고 싶을 때 도입
- 한 번에 여러 MCP를 설치하지 말고, **가장 필요한 것 하나**부터 시작

**3단계: Plugins (팀 단위로 확장하고 싶을 때)**
- Skills와 MCP 설정이 어느 정도 쌓였을 때, 이를 Plugin으로 묶어서 팀과 공유
- 개인용 → 팀용으로 자연스럽게 확장하는 단계

**4단계: Hooks (자동화가 정말 필요할 때)**
- 마지막 단계로 추천
- 자동화의 장점과 위험을 충분히 이해한 후에 도입하는 것이 안전

### 왜 이 순서인가?

- Skills는 실패 비용이 거의 없고, 학습 곡선이 완만합니다.
- MCP와 Hooks는 설정 실수나 보안 문제가 발생할 가능성이 상대적으로 높습니다.
- Plugins는 앞의 기능들이 어느 정도 쌓여야 의미가 있습니다.

“한 번에 다 하고 싶다”는 생각보다는, **하나씩 도입하면서 실제로 도움이 되는지 체감**하는 것이 훨씬 좋습니다.

## 10. 과도한 확장이 가져오는 위험

확장 기능은 강력하지만, **과도하게 사용하면 오히려 독이 될 수 있습니다**.

### 흔히 발생하는 문제들

- **복잡성 증가**  
  Skills, MCP, Hooks를 너무 많이 만들면, 나중에 “이게 왜 이렇게 동작하지?” 하는 상황이 자주 발생합니다.

- **유지보수 부담**  
  프로젝트가 바뀔 때마다 관련된 Skill과 Hook을 계속 수정해야 할 수 있습니다.

- **팀원들의 진입 장벽**  
  너무 많은 커스텀 규칙이 있으면, 새로운 팀원이 프로젝트에 적응하기 어려워집니다.

- **보안 위험**  
  특히 Hooks와 MCP는 잘못 설정하면 큰 보안 사고로 이어질 수 있습니다.

### 현실적인 조언

- **처음에는 최대 3~4개의 Skill**만 만드는 것부터 시작하세요.
- MCP 서버는 **정말 필요한 경우에만** 설치하세요.
- Hooks는 팀 전체가 동의한 후에 도입하세요.
- 1년에 한 번 정도는 “지금 쓰고 있는 확장 기능 중에 실제로 도움이 되는 게 뭐지?”를 점검해보세요.

**“확장 기능을 많이 쓰는 것”이 아니라, “필요한 확장 기능만 잘 쓰는 것”**이 진짜 실력입니다.

## 8.5 프로젝트 유형별 추천 조합

앞서 상황별 추천을 했지만, 실제로는 **프로젝트의 규모와 성격**에 따라 추천 조합이 달라집니다. 아래는 현실적인 프로젝트 유형별로 가장 효과적인 확장 기능 조합을 정리한 것입니다.

### 1. 1인 프로젝트 (개인 프로젝트)

**추천 조합**: **Skills + Memory** (가볍게 시작)

**추천 이유**:
- 혼자서 작업하므로 복잡한 팀 표준은 필요 없음
- 반복되는 작업(Skills)과 장기 기억(Memory)만으로도 생산성이 크게 향상됨
- 설정 부담이 적음

**추가 고려**:
- 나중에 프로젝트가 커지거나 다른 사람과 공유할 가능성이 생기면 Plugins를 추가
- MCP는 필요할 때만 하나씩 추가 (예: Git MCP, Filesystem MCP)

**시작 추천 순서**:
Skills → Memory (필요할 때) → MCP (필요할 때)

---

### 2. 소규모 팀 (3~8명)

**추천 조합**: **Skills + Plugins + AGENTS.md**

**추천 이유**:
- 팀 컨벤션을 통일해야 함
- Plugin 하나로 여러 Skill과 MCP 설정을 한 번에 배포할 수 있어서 관리 비용이 낮음
- AGENTS.md로 큰 방향을 정하고, Skill로 세부 절차를 정의하는 조합이 효과적

**추가 고려**:
- MCP는 팀 전체가 필요로 하는 것만 선별해서 Plugin에 포함
- Hooks는 팀 문화가 어느 정도 성숙한 후에 도입 (pre-commit 정도부터)

**시작 추천 순서**:
Skills (개인) → AGENTS.md (팀) → Plugins (배포) → MCP (필요한 것만) → Hooks (선택)

---

### 3. 중대형 팀 / 회사 (10명 이상)

**추천 조합**: **Plugins + AGENTS.md + Memory + Hooks (선별적)**

**추천 이유**:
- 팀 규모가 크기 때문에 표준화가 매우 중요
- Plugin으로 확장 기능을 체계적으로 관리하고 배포
- AGENTS.md로 아키텍처 방향과 기본 규칙을 명확히
- Memory로 반복되는 패턴과 결정을 축적
- Hooks는 신중하게 (pre-commit 정도만 팀 전체에 강제하고, 나머지는 선택)

**추가 고려**:
- Marketplace를 적극 활용하거나, 내부 전용 Marketplace를 구축
- Subagents는 일부 팀에서만 도입 (모든 팀원이 다룰 수 있는 수준이 아닐 수 있음)
- 보안 정책이 강한 회사의 경우 MCP와 Hooks 도입을 보안팀과 협의해야 함

**시작 추천 순서**:
AGENTS.md → Skills (팀 표준) → Plugins (배포) → Memory (패턴 축적) → Hooks (선별) → MCP (보안 검토 후)

---

### 4. 보안이 매우 중요한 프로젝트

**추천 조합**: **Skills + AGENTS.md + 최소한의 MCP + Sandbox**

**추천 이유**:
- MCP와 Hooks는 보안 위험이 높기 때문에 최소화
- Sandbox를 적극 활용하여 파일 시스템 접근 제한
- AGENTS.md와 Skills로 규칙을 강제하면서도 위험은 낮춤

**추가 고려**:
- MCP 서버는 읽기 전용 계정만 사용
- Hooks는 pre-commit 정도만 사용하고, 파일 수정이 발생하는 Hook은 피함
- Memory도 민감한 정보는 저장하지 않도록 주의

**시작 추천 순서**:
AGENTS.md → Skills → Sandbox → (필요 시) 제한된 MCP

---

### 5. 오픈소스 프로젝트

**추천 조합**: **Skills + AGENTS.md + Plugins (Marketplace 공개)**

- MCP는 공개하기 어려운 경우가 많아서 제한적으로 사용

**시작 추천 순서**:
AGENTS.md → Skills → Plugin (Marketplace 공개)

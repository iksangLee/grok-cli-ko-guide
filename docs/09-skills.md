# 08-스킬-만들고-사용하기

Grok Build를 사용하면서 반복되는 작업 패턴을 느끼게 되면, 자연스럽게 “이건 매번 설명하지 말고 미리 정해두면 좋겠다”는 생각이 들기 시작합니다.  
이때 필요한 것이 바로 **Skill**입니다.

이 문서는 단순히 “Skill이 뭐예요?”를 넘어, **실제로 좋은 Skill을 만들고, 잘 사용하고, 유지보수할 수 있는 수준**까지 도달하는 것을 목표로 합니다.

---

## 1. Skills란 무엇인가?

### Skill의 본질

Skill은 **“이 프로젝트(또는 이 상황)에서는 이렇게 행동해”** 라는 규칙과 패턴을 미리 정의해두는 것입니다.

일반적인 프롬프트와의 가장 큰 차이는 다음과 같습니다:

| 구분              | 일반 프롬프트                          | Skill                                      |
|-------------------|----------------------------------------|--------------------------------------------|
| 지속성            | 대화마다 매번 설명해야 함              | 한 번 만들어두면 계속 참고됨               |
| 일관성            | 모델의 기분(?)에 따라 결과가 달라짐    | 정해진 규칙을 따르기 때문에 일관됨        |
| 팀 공유           | 어렵다                                 | 파일로 존재하기 때문에 공유와 관리가 쉬움 |
| 복잡도            | 간단한 지시부터 복잡한 규칙까지 가능   | 복잡한 규칙일수록 Skill의 가치가 커짐      |

### 언제 Skill을 만들어야 할까?

아래 상황 중 하나 이상에 해당한다면, Skill을 만드는 것을 진지하게 고려해보세요.

- **반복되는 작업이 자주 발생한다**
  - 예: 매번 같은 스타일로 커밋 메시지를 작성
  - 예: 특정 프레임워크의 테스트 코드를 항상 같은 패턴으로 작성

- **프로젝트에 고유한 규칙이 있다**
  - “우리 팀은 절대 any를 쓰지 않는다”
  - “컴포넌트는 무조건 functional component + hooks로 작성”
  - “에러 처리는 항상 Result 타입으로 한다”

- **여러 사람이 함께 작업한다**
  - 새로운 팀원이 들어올 때마다 같은 설명을 반복하기 싫을 때
  - 코드 스타일을 통일하고 싶을 때

- **Grok이 자꾸 같은 실수를 한다**
  - 특정 패턴에서 계속 잘못된 코드를 제안할 때

### Skill을 만들면 얻는 실질적인 이점

1. **설명의 반복 제거** — 매번 긴 설명을 붙일 필요가 없음
2. **결과의 일관성** — 모델이 흔들려도 어느 정도 방향을 잡아줌
3. **팀 표준화** — 프로젝트의 코딩 철학을 파일로 명문화
4. **생산성 향상** — 특히 대규모 리팩터링이나 테스트 작성에서 체감이 큼

## 2. SKILL.md 파일 형식 완전 이해

Skill의 핵심은 `SKILL.md` 파일입니다.  
이 파일을 어떻게 작성하느냐에 따라 Skill의 품질이 크게 갈립니다.

### 기본 구조

```markdown
---
name: "프로젝트명-커밋-메시지"
description: "우리 프로젝트의 커밋 메시지 규칙을 따르는 커밋 메시지를 작성합니다."
version: "1.0.0"
---

# 커밋 메시지 작성 규칙

당신은 이 프로젝트의 Git 커밋 메시지를 작성하는 전문가입니다.

## 기본 규칙
- Conventional Commits 형식을 반드시 따르세요.
- 타입은 feat, fix, refactor, chore, docs, test, style 중 하나를 사용하세요.
- scope는 가능하면 붙이되, 불필요하면 생략하세요.
- 제목은 50자 이내로 작성하세요.
- 본문은 72자마다 줄바꿈을 하세요.

## 우리 프로젝트 특이사항
- React 프로젝트이므로, UI 변경 시에는 반드시 "ui" scope를 붙이세요.
- API 변경이 있을 때는 "api" scope를 사용하세요.
- breaking change가 있을 경우, 제목 앞에 "!"를 붙이고 본문에 자세한 설명을 작성하세요.

## 예시
<좋은 예시와 나쁜 예시를 여기에 작성>
```

### metadata 영역 상세 설명

| 필드          | 필수 | 설명 | 추천 작성 팁 |
|---------------|------|------|-------------|
| `name`        | O    | Skill의 고유 이름 | 영어 + 하이픈 조합 추천 (예: `team-commit-message`) |
| `description` | O    | 이 Skill이 어떤 일을 하는지 한 줄 요약 | Grok이 Skill을 선택할 때 참고하는 중요한 정보 |
| `version`     | X    | Skill의 버전 | 팀에서 관리할 때는 버전을 붙이는 것을 추천 |
| `author`      | X    | 만든 사람 | 개인용이 아니면 작성 |
| `tags`        | X    | 분류 태그 | `git`, `testing`, `refactoring` 등으로 태깅 가능 |

### 본문(prompt) 작성 시 중요한 원칙

**1. 역할(Role) 부여를 명확히 하라**
- 나쁜 예: “커밋 메시지를 작성해줘”
- 좋은 예: “당신은 이 프로젝트의 Git 히스토리를 관리하는 시니어 개발자입니다. 커밋 메시지를 작성할 때는 항상 팀의 컨벤션을 최우선으로 따릅니다.”

**2. 규칙은 구체적으로, 예시는 풍부하게**
- 추상적인 규칙만 나열하지 말고, **“이런 경우에는 이렇게 하라”**는 구체적인 지시를 포함하세요.
- 좋은 예시와 나쁜 예시를 함께 넣으면 효과가 매우 좋습니다.

**3. 프로젝트의 맥락을 충분히 담아라**
- “우리 프로젝트는 React + TypeScript + Vitest를 사용합니다.”
- “상태 관리는 Zustand를 사용하며, 컴포넌트는 최대한 작게 유지하는 것을 지향합니다.”

**4. 출력 형식까지 지정하라**
- 어떤 형식으로 답변해야 하는지 명확히 알려주세요.
- “설명 없이 커밋 메시지만 출력해” 또는 “변경 이유에 대한 간단한 설명도 함께 작성해” 같은 지시가 필요합니다.

## 3. Skill 만들기 - 기본 과정

이제 실제로 Skill을 하나 만들어보겠습니다.

### 추천 폴더 구조

Grok Build는 다음과 같은 위치에서 Skill을 인식합니다:

- `~/.grok/skills/` — 전역 Skill (모든 프로젝트에서 사용 가능)
- `<프로젝트 루트>/.grok/skills/` — 프로젝트 전용 Skill (해당 프로젝트에서만 사용)

**개인 프로젝트**라면 프로젝트 루트에 `.grok/skills/` 폴더를 만드는 것을 추천합니다.

### 첫 Skill 만들기 (Step by Step)

**예시: Git 커밋 메시지 Skill 만들기**

1. **폴더 생성**
   ```bash
   mkdir -p .grok/skills/commit-message
   ```

2. **`SKILL.md` 파일 생성**
   ```bash
   touch .grok/skills/commit-message/SKILL.md
   ```

3. **내용 작성** (아래는 기본적인 예시)

```markdown
---
name: "commit-message"
description: "우리 프로젝트의 커밋 메시지 규칙에 맞춰서 커밋 메시지를 작성합니다."
version: "1.0.0"
---

# 커밋 메시지 작성 규칙

당신은 이 프로젝트의 Git 커밋 메시지를 책임지는 개발자입니다.

## 필수 규칙
- Conventional Commits 형식을 반드시 따르세요.
- 타입은 다음 중 하나만 사용: feat, fix, refactor, chore, docs, test, style
- scope는 의미가 명확할 때만 붙이세요.
- 제목은 50자 이내로 작성하세요.

## 우리 프로젝트 특이사항
- 이 프로젝트는 React + TypeScript + Tailwind를 사용합니다.
- UI 변경 시에는 반드시 `ui` scope를 붙이세요.
- API 변경 시에는 `api` scope를 사용하세요.
- breaking change가 있을 경우 제목에 `!`를 붙이고, 본문에 마이그레이션 가이드를 작성하세요.

## 출력 형식
- 설명 없이 커밋 메시지만 출력하세요.
- 여러 커밋이 필요한 경우, 각 커밋 메시지를 구분해서 보여주세요.
```

4. **Skill 로드 확인**
   - Grok Build를 재시작하거나, `/reload` 명령어를 사용하면 Skill이 인식됩니다.
   - `Ctrl + L` → Skills 탭에서 새로 만든 Skill이 보이는지 확인하세요.

5. **실제로 사용해보기**
   ```
   이 변경사항에 대한 커밋 메시지를 작성해줘
   ```

Grok이 Skill에 정의된 규칙을 참고해서 커밋 메시지를 작성한다면 성공입니다.

### 처음 Skill을 만들 때 흔히 하는 실수

- 너무 많은 규칙을 한 번에 넣으려고 함
- “무조건 이렇게 해” 식의 강압적인 표현만 사용
- 프로젝트의 실제 코드 스타일을 반영하지 않음
- 예시를 전혀 넣지 않음

처음에는 **규칙 3~4개 + 좋은 예시 2개 + 나쁜 예시 1개** 정도로 시작하는 것을 추천합니다.

## 4. 실전 Skills 예시 모음 (사용 빈도가 높은 스킬 위주)

이 섹션에서는 실제로 많은 개발자들이 자주 만들고, 효과를 크게 보는 **고빈도 스킬**들을 중심으로 상세한 예시를 제공합니다.

각 예시는 “그냥 복사해서 써도 어느 정도 돌아가는” 수준이 아니라, **실제 프로젝트에 맞게 커스터마이징하기 좋은** 형태로 작성했습니다.

### 4.1 Git Commit Message Skill (가장 추천)

**사용 빈도**: ★★★★★

대부분의 개발자가 가장 먼저 만들게 되는 Skill입니다.

**SKILL.md 예시** (Conventional Commits + 프로젝트 규칙)

```markdown
---
name: "git-commit-message"
description: "프로젝트의 커밋 메시지 규칙을 철저히 따르는 커밋 메시지를 작성합니다."
version: "1.2.0"
---

# Git 커밋 메시지 작성 규칙

당신은 이 프로젝트의 Git 히스토리를 책임지는 시니어 개발자입니다.

## 필수 형식
- Conventional Commits 형식을 **반드시** 따르세요.
- 허용된 타입: feat, fix, refactor, chore, docs, test, style, perf, build, ci
- scope는 가능하면 붙이되, 애매하면 생략하세요.
- 제목은 **50자 이내**, 본문은 **72자마다 줄바꿈**.

## 우리 프로젝트 특이사항 (중요)
- React + TypeScript + Tailwind CSS 프로젝트입니다.
- UI 관련 변경 → `ui` scope 필수
- API 변경 → `api` scope 사용
- 상태 관리(Zustand) 변경 → `state` scope
- breaking change 발생 시 제목에 `!`를 붙이고, 본문에 마이그레이션 가이드를 반드시 작성

## 품질 기준
- "update", "fix bug", "change" 같은 모호한 단어 사용 금지
- "what"이 아니라 "why"를 중심으로 작성
- 테스트가 추가되거나 변경된 경우, test scope 또는 본문에 테스트 관련 내용 포함

## 출력 형식
- 설명 없이 커밋 메시지만 출력
- 여러 커밋이 필요한 경우, `---`로 구분해서 보여주기
```

**사용 팁**:
- 변경사항을 `@`로 파일 몇 개 붙여서 물어보면 훨씬 좋은 결과를 얻습니다.
- “이 변경에 대한 커밋 메시지 2~3개 후보를 만들어줘”라고 하면 선택의 폭이 생깁니다.

### 4.2 Unit Test Generation Skill

**사용 빈도**: ★★★★★

테스트 작성 부담을 크게 줄여주는 스킬입니다.

**SKILL.md 예시** (React + Vitest + Testing Library 기준)

```markdown
---
name: "unit-test-generation"
description: "프로젝트의 테스트 스타일과 컨벤션을 따르는 단위 테스트를 작성합니다."
version: "1.0.0"
---

# 단위 테스트 작성 규칙

당신은 이 프로젝트의 테스트 품질을 책임지는 QA + 개발자입니다.

## 테스트 프레임워크 및 스타일
- Vitest + @testing-library/react 사용
- 테스트 파일은 `__tests__` 폴더 또는 `.test.ts` 확장자 사용
- describe → it → expect 구조를 기본으로 함
- 각 it()은 **하나의 행동**만 테스트해야 함

## 우리 프로젝트 테스트 원칙
- "should"로 시작하는 테스트 설명 사용
- props drilling이나 복잡한 상태는 mock으로 처리
- 비동기 코드는 `await` + `findBy` 계열 사용
- userEvent를 우선적으로 사용 (fireEvent는 특수한 경우에만)

## 피해야 할 패턴
- 테스트에서 실제 API 호출 금지 (항상 mock)
- 컴포넌트 내부 구현(private 함수, state)에 의존하는 테스트 금지
- 너무 많은 것을 한 번에 테스트하는 "God test" 금지

## 출력 형식
- 설명 없이 테스트 코드만 출력
- 필요한 import도 함께 포함
```

**사용 팁**:
- 테스트를 작성하고 싶은 컴포넌트/함수 파일을 `@`로 붙여서 요청하면 훨씬 정확합니다.
- “이 컴포넌트의 happy path와 edge case 테스트를 작성해줘”라고 구체적으로 말하면 좋습니다.

### 4.3 Code Review / PR Description Skill

**사용 빈도**: ★★★★☆

PR을 올릴 때마다 반복되는 작업을 자동화할 수 있습니다.

**SKILL.md 예시**

```markdown
---
name: "pr-description-and-review"
description: "변경사항을 분석하여 PR 설명과 리뷰 포인트를 작성합니다."
---

# PR 설명 및 코드 리뷰 작성 규칙

당신은 이 프로젝트의 기술 리더입니다.

## PR 설명 작성 기준
- What: 어떤 변경을 했는지
- Why: 왜 이 변경이 필요한지 (비즈니스 + 기술적 이유)
- How: 주요 구현 방식
- Breaking change 여부 명시
- 스크린샷이나 데모가 필요한지 판단

## 코드 리뷰 포인트 작성 기준
- 잠재적인 버그 가능성
- 성능 이슈
- 가독성 / 유지보수성 문제
- 보안 위험
- 테스트 부족 영역
- 아키텍처 일관성 위반

## 출력 형식
1. PR 제목 후보 2개
2. PR 본문 (마크다운)
3. 주요 리뷰 포인트 (체크리스트 형식)
```

이 스킬은 PR을 올리기 전에 변경된 파일들을 `@`로 여러 개 붙여서 사용하면 매우 유용합니다.

### 4.4 Documentation Generation Skill

**사용 빈도**: ★★★★

함수, 컴포넌트, API에 대한 문서화를 도와줍니다.

**추천하는 주요 유형**:
- JSDoc / TSDoc 자동 생성
- README 섹션 작성
- API 문서화
- 복잡한 로직에 대한 주석

이 스킬은 특히 **공개 API**나 **복잡한 유틸리티 함수**를 많이 다루는 프로젝트에서 효과가 좋습니다.

## 6. Skill과 다른 확장 기능 연동

Skill은 단독으로도 강력하지만, 다른 확장 기능과 함께 사용하면 훨씬 더 큰 시너지를 발휘합니다.

### 6.1 Skill + MCP Servers

**가장 강력한 조합 중 하나**

- Skill로 “어떻게 동작해야 하는지” 규칙을 정의
- MCP Server로 “실제 데이터를 읽고 쓰는 능력”을 부여

**예시 조합**:
- Skill: “데이터베이스 쿼리를 작성할 때는 항상 parameter를 사용하고, raw query를 금지한다”
- MCP: PostgreSQL MCP 서버

→ Grok이 실제 DB에 접근하면서도, Skill에 정의된 안전한 쿼리 작성 규칙을 따르게 할 수 있습니다.

### 6.2 Skill + Hooks

**자동화 + 품질 보증**

- Hook: pre-commit 시점에 특정 파일이 변경되면 자동으로 테스트 실행
- Skill: 테스트가 실패하면, 실패 원인을 분석하고 수정 제안을 해주는 역할

이 조합은 “자동으로 검사 + 자동으로 개선 제안”이라는 강력한 흐름을 만들 수 있습니다.

### 6.3 Skill + Plugins

**팀 표준화의 핵심**

팀에서 자주 사용하는 여러 Skill을 하나로 묶어서 Plugin으로 배포할 때, Skill은 Plugin의 가장 중요한 구성 요소 중 하나가 됩니다.

예: `team-frontend-standards` 플러그인 안에
- git-commit-message Skill
- unit-test-generation Skill
- refactor-props-drilling Skill
- docs-jsdoc Skill

이렇게 묶어서 팀원들에게 배포하면, 프로젝트마다 일일이 Skill을 만들 필요가 없습니다.

### 6.4 Skill + AGENTS.md

AGENTS.md은 프로젝트 전체에 적용되는 **상위 규칙**이고, Skill은 특정 작업에 특화된 **하위 규칙**입니다.

둘을 잘 조합하면:
- AGENTS.md: “이 프로젝트의 전체적인 철학과 아키텍처 방향”
- Skill: “특정 작업(커밋, 테스트, 리뷰)을 할 때의 구체적인 실행 규칙”

이렇게 계층을 나누는 것이 가장 이상적입니다.

## 7. Skill 디버깅 및 테스트 방법

Skill을 만들었는데 기대한 대로 동작하지 않을 때, 아래 순서로 확인해보세요.

### 디버깅 체크리스트

1. **Skill이 로드되었는지 확인**
   - `Ctrl + L` → Skills 탭에서 Skill이 보이는지 확인
   - 보이지 않으면 폴더 구조나 `SKILL.md` 파일명이 정확한지 확인

2. **description이 너무 모호한지 확인**
   - description이 “프로젝트 도와주는 스킬”처럼 vague하면 Grok이 언제 이 Skill을 불러야 할지 판단하기 어렵습니다.
   - description은 **“언제 이 Skill을 사용해야 하는지”**를 명확히 설명해야 합니다.

3. **규칙이 모순되거나 너무 많지 않은지 확인**
   - 규칙이 15개가 넘어가면 Grok이 혼란스러워하는 경우가 많습니다.
   - 처음에는 4~7개의 핵심 규칙으로 시작하는 것이 좋습니다.

4. **예시가 부족한지 확인**
   - 좋은 예시와 나쁜 예시가 부족하면, Grok이 “이게 좋은 건지 나쁜 건지” 판단하기 어렵습니다.
   - 가능하면 2~3개의 좋은 예시 + 1개의 나쁜 예시를 넣는 것을 추천합니다.

5. **@로 파일을 충분히 붙였는지 확인**
   - Skill이 동작하려면 프로젝트의 실제 코드 스타일을 알아야 하는 경우가 많습니다.
   - 관련 파일을 `@`로 붙여서 요청하면 훨씬 정확한 결과를 얻을 수 있습니다.

### Skill 테스트 방법

- 작은 변경사항을 만들어서 Skill을 여러 번 호출해보기
- “이 규칙을 지키지 않은 예시를 만들어서 테스트해봐”라고 요청해서 Skill이 잘 걸러내는지 확인
- 팀원 1~2명에게 실제로 사용하게 해보고 피드백 받기

## 8. Best Practices & Anti-patterns

### Best Practices (잘 만드는 법)

- **하나의 Skill은 하나의 명확한 책임을 가진다**
- **description을 구체적으로 작성** (Grok이 Skill을 선택하는 데 가장 중요한 정보)
- **프로젝트의 실제 코드 스타일을 반영** (추상적인 규칙보다는 구체적인 예시가 훨씬 효과적)
- **예시를 충분히 넣는다** (좋은 예시 2~3개 + 나쁜 예시 1개)
- **버전 관리**를 한다 (특히 팀에서 사용할 때)
- **작게 시작해서 점진적으로 확장**한다

### Anti-patterns (피해야 할 패턴)

- **God Skill**: 모든 것을 다 하려는 Skill (규칙 20개 이상)
- **Vague Skill**: “프로젝트를 도와줘” 같은 모호한 Skill
- **Overlapping Skill**: 비슷한 역할을 하는 Skill이 여러 개 있어서 충돌
- **예시 없는 Skill**: 규칙만 잔뜩 나열하고 예시가 거의 없는 경우
- **너무 자주 바꾸는 Skill**: 프로젝트가 조금만 바뀌어도 Skill을 대대적으로 수정해야 하는 경우

### `/skillify`

`/skillify`는 **현재 세션에서 진행한 워크플로를 자동으로 Skill로 추출**해주는 매우 강력한 명령어입니다.

```bash
/skillify
/skillify deploy workflow for k8s
```

**두 가지 모드**:
- **From-session mode**: 이미 워크플로를 진행한 세션에서 사용하면, Grok이 tool calls, 파일 변경, 명령 실행 등을 분석해서 Skill을 제안합니다.

- `name`, `description`, `when-to-use`, `allowed-tools`, `argument-hint`, `arguments` 등의 상세 frontmatter가 자동 생성됩니다.
- 각 단계에 success criteria와 human checkpoint가 포함될 수 있습니다.

**Best Practices**:
- 워크플로가 끝난 **직후**에 `/skillify`를 실행하세요. (세션 히스토리가 compaction되기 전에)
- Project scope(`<repo_root>/.grok/skills/`)로 저장하면 팀과 공유하기 좋습니다.

## 배경 지식: 이 기능이 왜 이렇게 동작하는가

> **참고**: 이 섹션은 Grok 공식 문서에 명시된 설계 의도를 그대로 설명한 것이 아닙니다.  
> 실제 동작 방식과 관찰, 그리고 논리적 해석을 바탕으로 작성한 **참고용 설명**입니다.  
> xAI에서 공식적으로 발표한 설계 철학이 아니라는 점을 참고해 주세요.

Skill 시스템이 현재와 같은 형태로 제공되는 배경과 특징을 정리했습니다.

### 1. 왜 description으로 자동 호출이 결정되나?

Grok은 사용자의 프롬프트를 보고, "이 작업에 적합한 Skill이 있는가?"를 판단합니다.  
이때 가장 중요한 기준이 바로 Skill의 `description` 필드입니다.

description을 구체적으로 작성하면:
- Grok이 언제 이 Skill을 불러야 할지 더 정확하게 판단할 수 있습니다.
- 불필요한 Skill이 호출되는 것을 줄일 수 있습니다.
- 팀원이 Skill을 보고 "이건 언제 쓰는 거지?"를 바로 이해할 수 있습니다.

### 2. 왜 AGENTS.md, Skill, Memory를 구분해서 쓰나?

- **AGENTS.md**: 프로젝트 전체에 **영구적으로 적용**되는 큰 규칙 (아키텍처, 철학, 기본 컨벤션)
- **Skill**: 특정 **작업**이나 **상황**에 특화된 절차와 패턴
- **Memory**: 프로젝트를 하면서 **발견한 사실**이나 **경험**을 축적하는 것

이 세 가지는 목적과 지속 기간이 다르기 때문에, 섞어서 사용하면 오히려 혼란스러워질 수 있습니다.  
각자의 역할을 명확히 구분해서 쓰는 것이 장기적으로 관리하기 좋습니다.

### 3. 왜 `/skillify`가 유용한가?

대부분의 사람은 "이 작업을 어떻게 하는지"를 머릿속으로만 가지고 있습니다.  
`/skillify`는 그 워크플로를 **명시적인 Skill 파일**로 만들어주는 도구입니다.

이 기능을 사용하면, 매번 같은 설명을 반복하거나 처음부터 수동으로 Skill을 작성하는 수고를 줄일 수 있습니다.  
`/skillify`는 "생각을 파일로 만드는" 과정을 상당히 빠르게 해주는 편리한 기능입니다.

### Skill이 호출되지 않을 때

   - "프로젝트 도와주는 스킬"처럼 vague하면 Grok이 언제 불러야 할지 판단하기 어렵습니다.
   - "이 프로젝트에서 커밋 메시지를 작성할 때 사용"처럼 구체적으로 작성하세요.

2. **Skill이 제대로 로드되었는지 확인**
   ```bash
   grok inspect
   ```
   - Skill이 보이지 않으면 파일 위치, 이름(`SKILL.md`), frontmatter 형식을 확인하세요.

3. **@로 충분한 파일을 붙였는지 확인**
   - Skill이 프로젝트의 스타일을 알아야 하는 경우, 관련 파일을 `@`로 붙여주면 훨씬 정확하게 동작합니다.

### Skill이 이상한 결과를 낼 때

1. **예시가 부족한지 확인**
   - 규칙만 잔뜩 적고 예시가 거의 없으면, Grok이 "이게 좋은 건지 나쁜 건지" 헷갈리는 경우가 있습니다.
   - 좋은 예시 2~3개와 나쁜 예시 1개를 함께 넣는 것이 경험상 도움이 되는 경우가 많습니다.

2. **규칙이 모순되거나 너무 많은지 확인**
   - 규칙이 15개 이상으로 많아지면 Grok이 모두 일관되게 지키기 어려워질 수 있습니다.
   - 처음에는 핵심 규칙 5~7개 정도로 시작해서, 필요할 때 점차 늘려가는 것을 추천합니다.

3. **description과 실제 내용이 일치하는지 확인**
   - description에는 "PR 리뷰를 도와주는 스킬"이라고 써놓고, 실제로는 커밋 메시지 작성 규칙만 들어있는 경우가 있습니다.
   - description과 내용의 일관성을 맞추세요.

### Skill이 아예 로드되지 않을 때

- 파일 이름이 정확히 `SKILL.md`인지 확인
- YAML frontmatter(`---`)가 제대로 닫혔는지 확인
- `name` 필드가 64자 이하인지, 특수문자가 없는지 확인
- 프로젝트 루트나 `~/.grok/skills/` 폴더 안에 있는지 확인

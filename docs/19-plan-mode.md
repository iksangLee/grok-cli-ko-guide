# 18-계획 모드

Grok Build를 사용하다 보면, 가끔 **"이 작업을 어떻게 접근해야 할지"**가 명확하지 않은 경우가 있습니다.

예를 들어:
- "사용자 인증을 추가해줘" (JWT? Session? OAuth? 어디에 저장할까?)
- "데이터 파이프라인을 새로 설계해줘" (어떤 아키텍처가 좋을까?)
- "API에 캐싱을 추가해줘" (Redis? In-memory? 파일 기반?)

이런 작업은 **구현 방법이 여러 가지**이고, **잘못된 방향으로 가면 큰 손해**를 볼 수 있습니다.

이럴 때 사용하는 것이 바로 **Plan Mode**입니다.

---

## Plan Mode란 무엇인가?

**Plan Mode**는 Grok이 **코드를 실제로 수정하기 전에**, 먼저 계획을 세우고 사용자에게 승인을 받는 모드입니다.

### Plan Mode가 활성화되면?

1. Grok은 코드베이스를 **자유롭게 읽고 검색**할 수 있습니다.
2. 하지만 **파일을 수정하거나 명령을 실행할 수 없습니다**. (plan.md 파일에만 쓸 수 있음)
3. Grok은 `plan.md` 파일에 **구조화된 구현 계획**을 작성합니다.
4. 계획이 완성되면 사용자에게 제시하고 **승인을 기다립니다**.
5. 사용자가 승인하면 실제 구현을 시작합니다. (수정하거나 거절할 수도 있음)

이렇게 **계획 단계와 구현 단계를 분리**하면, 모호하거나 큰 작업에서 **불필요한 수정을 줄일 수** 있습니다.

---

## Plan Mode가 왜 유용한가?

### 1. 큰 리팩터링에서 방향을 잃지 않게 해줌

예: "이 프로젝트의 인증 시스템을 완전히 새로 만들자"

- JWT? Session? OAuth?
- 토큰은 어디에 저장?
- Refresh Token 전략은?
- Middleware 구조는?

이런 결정은 **구현을 시작하기 전에** 명확히 해야 합니다. Plan Mode는 이 과정을 체계적으로 도와줍니다.

### 2. 아키텍처 결정에서 실수를 줄임

예: "데이터 파이프라인을 새로 설계해줘"

- ETL? ELT?
- Batch? Streaming?
- 어떤 기술 스택?

이런 결정은 잘못 내리면 나중에 큰 비용이 발생합니다. Plan Mode는 여러 옵션을 탐색하고, 장단점을 정리한 뒤 사용자에게 제시합니다.

### 3. 팀 협업에서 계획을 명확히 공유할 수 있음

Plan Mode로 생성된 `plan.md`는 팀원들과 공유하기에도 좋습니다. "Grok이 이렇게 계획했는데, 어떻게 생각해?"라고 물어볼 수 있습니다.

---

## Plan Mode 진입 조건

### 1. 자동 진입 (가장 흔한 경우)

Grok이 작업을 분석하다가 **"이건 계획이 필요한 작업이야"**라고 판단하면, 자동으로 `enter_plan_mode` 도구를 호출합니다.

이때 사용자에게 **"Plan Mode로 들어가도 될까요?"**라고 물어봅니다. 사용자가 승인해야 Plan Mode가 시작됩니다.

**Plan Mode에 적합한 작업 예시**:
- "사용자 인증을 추가해줘"
- "데이터 파이프라인을 새로 설계해줘"
- "API에 캐싱을 추가해줘"
- "실시간 업데이트 기능을 넣어줘"

**Plan Mode에 적합하지 않은 작업 예시**:
- "유저 프로필에 삭제 버튼을 추가해줘" (명확한 구현 경로)
- "README의 오타를 수정해줘" (단순한 작업)
- "API의 에러 처리를 업데이트해줘" (이미 시작해도 됨)

### 2. 수동 진입

사용자가 명시적으로 "이 작업은 계획을 먼저 세워줘"라고 요청하면, Grok이 Plan Mode로 들어갈 수 있습니다.

(현재는 `/plan` 같은 슬래시 명령어는 없으며, Grok이 자동으로 판단하거나 사용자가 자연스럽게 요청하는 방식입니다.)

---

## Plan File (`plan.md`)

Plan Mode에서 Grok이 작성하는 계획서는 **세션 디렉토리** 안에 `plan.md`라는 파일로 저장됩니다.

경로 예시:
```
~/.grok/sessions/<인코딩된-작업-디렉토리>/<세션-ID>/plan.md
```

### Plan Mode가 활성화되면?

- Grok은 이 `plan.md` 파일에만 내용을 쓸 수 있습니다.
- 다른 파일을 수정하거나, shell 명령을 실행하는 것은 **완전히 차단**됩니다.
- Grok은 코드베이스를 탐색하면서 `plan.md`에 구조화된 계획을 작성합니다.

### Plan Mode 종료

- Grok이 계획을 완성하면 사용자에게 제시합니다.
- 사용자가 승인하면 Plan Mode가 종료되고, 일반 모드로 전환되어 실제 구현을 시작합니다.
- 사용자가 "이 부분은 이렇게 바꿔줘"라고 피드백하면, Grok이 계획을 수정합니다.

## Plan Mode에서 Grok이 실제로 어떤 계획을 작성하는가?

Plan Mode가 활성화되면, Grok은 `plan.md` 파일에 **구조화된 구현 계획**을 작성합니다.

### plan.md의 일반적인 구조

```markdown
# Implementation Plan: 사용자 인증 추가

## 1. Overview
- 이 작업의 목표
- 왜 이 작업이 필요한지
- 예상되는 영향 범위

## 2. Current State Analysis
- 현재 인증 관련 코드가 어디에 있는지
- 어떤 파일을 수정해야 하는지
- 기존에 어떤 인증 방식이 사용되고 있는지

## 3. Design Decisions
- 어떤 인증 방식을 사용할 것인가? (JWT vs Session vs OAuth)
- 토큰/세션은 어디에 저장할 것인가?
- Middleware 구조는 어떻게 할 것인가?
- 에러 처리 전략은?

## 4. Implementation Steps
1. Auth Service 생성
2. JWT 유틸리티 작성
3. Middleware 구현
4. Route 보호 로직 추가
5. 테스트 작성

## 5. Files to Modify
- `src/auth/jwt.ts` (new)
- `src/middleware/auth.ts` (new)
- `src/routes/user.ts` (modify)
- ...

## 6. Risks & Considerations
- 보안 위험
- 성능 영향
- 마이그레이션 전략

## 7. Testing Strategy
- Unit test
- Integration test
- E2E test
```

### Plan Mode가 작성하는 계획의 특징

- **단계별**로 나누어져 있음
- **파일 단위**로 어떤 것을 수정/생성할지 명시
- **위험 요소**를 미리 분석
- **대안**을 제시하는 경우도 많음

---

## Plan File의 구조와 작성 스타일

### plan.md 파일 위치

```
~/.grok/sessions/<인코딩된-작업-디렉토리>/<세션-ID>/plan.md
```

### Plan Mode 중에 할 수 있는 일

Plan Mode가 활성화된 동안, Grok은:

- 코드베이스 전체를 **읽고 검색**할 수 있음 (`read_file`, `grep`, `list_dir` 등)
- `plan.md` 파일에만 내용을 **추가/수정**할 수 있음
- 다른 파일을 수정하거나 shell 명령을 실행하는 것은 **완전히 차단**됨

### Plan Mode 종료 조건

- Grok이 계획을 완성하고 사용자에게 제시
- 사용자가 승인 → Plan Mode 종료 + 일반 모드 전환
- 사용자가 피드백 제공 → Grok이 계획 수정
- 사용자가 "이제 구현해"라고 말하면 → Plan Mode 종료 + 구현 시작

---

## Plan Mode에서 사용자 피드백 주고받는 방법

Plan Mode의 가장 큰 장점은 **사용자가 계획을 검토하고 수정할 수 있다는 점**입니다.

### 사용자 피드백 예시

**Grok이 계획을 제시한 후:**

```
Plan Mode가 완료되었습니다. 
`plan.md` 파일에 구현 계획을 작성했습니다. 
이 계획을 승인하시겠습니까? 
아니면 수정이 필요한 부분이 있나요?
```

**사용자가 피드백을 주는 경우:**

```
"3단계의 Middleware 구조는 이렇게 하지 말고, HOC 패턴으로 가는 게 어때?"
"보안 부분에서 JWT Refresh Token 전략이 빠진 것 같아. 그 부분도 추가해줘."
```

Grok은 사용자의 피드백을 반영해서 `plan.md`를 업데이트합니다.

### Plan Mode를 활용하는 좋은 습관

- **큰 작업은 Plan Mode로 먼저 시작**하는 습관을 들이세요.
- 계획이 나오면 **바로 승인하지 말고**, 한 번 읽어보고 수정할 부분이 있는지 생각해보세요.
- "이 부분은 이렇게 하는 게 좋을 것 같아"라고 구체적으로 피드백하면, Grok이 더 좋은 계획을 세웁니다.

---

## Plan Mode와 일반 모드의 전환 흐름

1. **일반 모드** → Grok이 작업을 분석하다가 "이건 Plan Mode가 필요해"라고 판단
2. **Plan Mode 진입** → 사용자 승인 (자동 또는 수동)
3. **Plan Mode 활성화** → `plan.md`에만 쓰기 가능, 다른 파일 수정 불가
4. **계획 작성** → Grok이 코드베이스 탐색 + 계획 수립
5. **사용자 검토** → 계획을 읽고, 피드백 제공 또는 승인
6. **Plan Mode 종료** → 일반 모드로 전환
7. **구현 시작** → 이제 실제로 파일을 수정하고 명령을 실행할 수 있음

이 흐름을 이해하면, Plan Mode가 **"계획 → 승인 → 실행"**의 명확한 단계를 제공한다는 것을 알 수 있습니다.

---


지금까지 Plan Mode에서 Grok이 실제로 어떤 계획을 작성하는지, Plan File의 구조, 사용자 피드백 주고받는 방법, 그리고 Plan Mode와 일반 모드의 전환 흐름을 다루었습니다.

## Plan Mode에서 사용할 수 있는 모든 옵션과 고급 설정

### Plan Mode 관련 옵션

Plan Mode는 대부분 자동으로 진입되지만, 사용자가 제어할 수 있는 몇 가지 옵션이 있습니다.

- **자동 Plan Mode 비활성화** (config.toml)
  ```toml
  [plan_mode]
  auto_enter = false
  ```

- **강제 Plan Mode 진입** (현재는 자연어로 요청하는 방식)
  - "이 작업은 먼저 계획을 세워줘"라고 명시적으로 요청하면 Grok이 Plan Mode로 들어갈 수 있습니다.

### 고급 설정

- `plan.md` 파일 위치는 세션 디렉토리 안에 고정되어 있습니다.
- Plan Mode 중에는 `plan.md` 파일에만 쓰기가 허용되고, 다른 파일 수정은 완전히 차단됩니다.
- Plan Mode 종료 후에는 일반 모드로 전환되어 실제 구현이 시작됩니다.

## Plan Mode vs 일반 모드 vs 다른 기능 비교

| 구분            | 일반 모드 (TUI)           | Plan Mode                    | Subagent                     |
|-----------------|---------------------------|------------------------------|------------------------------|
| 목적            | 바로 구현                 | 계획 먼저 세우기             | 병렬 작업 위임               |
| 파일 수정       | 가능                      | `plan.md`에만 가능           | 독립 세션에서 가능           |
| 컨텍스트        | 메인 세션 컨텍스트        | 메인 세션 컨텍스트           | 독립 컨텍스트                |
| 사용자 개입     | 실시간                    | 계획 승인 단계에서 개입      | 결과 검토 단계에서 개입      |
| 적합한 작업     | 명확한 구현 경로          | 모호하거나 큰 작업           | 병렬 처리 가능한 작업        |

**한 줄 요약**:
- **일반 모드**: 바로 시작
- **Plan Mode**: 계획 먼저
- **Subagent**: 병렬로 위임

## Plan Mode 사용 시 Best Practices & Anti-patterns

### Best Practices

- **모호한 작업은 Plan Mode로 먼저 시작**하라
- **계획을 바로 승인하지 말고 검토**하라
- **구체적인 피드백을 주라** ("이렇게 바꿔줘"가 "이건 별로야"보다 훨씬 효과적)
- **Plan Mode 중에도 중요한 결정은 사용자와 상의**하라
- **계획이 너무 길면 나누어서** 진행하라

### Anti-patterns

- **Plan Mode를 너무 자주 사용**하지 마라 (단순한 작업까지 Plan Mode로 들어가면 오히려 느려짐)
- **피드백 없이 그냥 승인**하지 마라 (Grok이 놓친 부분이 있을 수 있음)
- **Plan Mode에서 너무 많은 것을 기대**하지 마라 (Grok도 완벽하지 않음)
- **계획을 너무 추상적으로** 작성하지 마라 (구체적인 파일/단계가 있어야 실행 가능)

### Plan Mode 추천 사용처

- 큰 리팩터링
- 아키텍처 변경
- 모호한 요구사항
- 팀 협업이 필요한 작업

**18-계획-모드.md 끝**

여기까지 Grok Build의 Plan Mode를 실전 관점에서 정리했습니다.

Plan Mode는 Grok Build를 단순한 "코딩 도구"에서 **생각하고 계획하는 AI 파트너**로 만들어주는 중요한 기능입니다.

이제 Grok Build의 주요 실행 모드(TUI, Headless, Agent Mode)와 확장 기능(Skills, MCP, Plugins, Hooks, Memory, Project Rules, Subagents, Plan Mode)을 모두 살펴보았습니다.

필요한 부분부터 하나씩 도입하면서, 자신만의 개발 환경을 만들어가시길 응원합니다.

이 문서에서 다루지 않은 더 고급 활용법이나 특정 상황에서의 Plan Mode 전략이 필요하시면 언제든 말씀해주세요.

## 배경 지식: 이 기능이 왜 이렇게 동작하는가

> **참고**: 이 섹션은 Grok 공식 문서에 명시된 설계 의도를 그대로 설명한 것이 아닙니다.  
> 실제 동작 방식과 관찰, 그리고 논리적 해석을 바탕으로 작성한 **참고용 설명**입니다.  
> xAI에서 공식적으로 발표한 설계 철학이 아니라는 점을 참고해 주세요.

Plan Mode가 현재와 같은 형태로 제공되는 배경과 특징을 정리했습니다.

### 1. 왜 Plan Mode가 필요한가?

Grok은 강력한 코드 작성 능력을 가지고 있지만, **모호한 요청**을 받으면 잘못된 방향으로 빠르게 구현을 진행할 위험이 있습니다.

예를 들어 “사용자 인증을 추가해줘”라는 요청은:
- JWT를 쓸지, Session을 쓸지
- 토큰을 어디에 저장할지
- Middleware 구조를 어떻게 할지

이런 결정이 **구현을 시작하기 전에** 명확해야 합니다. Plan Mode는 이 “생각하는 단계”를 강제로 분리해서, 큰 손해를 보기 전에 방향을 잡을 수 있게 해줍니다.

### 2. 왜 plan.md 파일에만 쓰기가 허용되나?

Plan Mode에서는 Grok이 실제 파일을 수정하거나 shell 명령을 실행하는 것을 **완전히 차단**합니다.

이유는 단순합니다: **계획 단계에서는 실수를 해도 복구가 쉽지만, 구현 단계에서 실수하면 이미 코드가 망가져 있을 수 있기 때문**입니다.

`plan.md`에만 쓰도록 제한하면, Grok은 자유롭게 코드를 읽고 탐색하면서도, 사용자가 승인하기 전까지는 아무것도 망치지 못합니다.

### 3. 왜 자동으로 Plan Mode에 진입하나?

Grok은 사용자의 프롬프트를 분석해서 “이건 계획이 필요한 작업이다”라고 판단하면 `enter_plan_mode` 도구를 호출합니다.

이건 사용자 경험을 고려한 동작입니다. 매번 “Plan Mode로 들어갈까요?”라고 묻지 않고, Grok이 스스로 판단해서 제안하는 방식을 택한 것으로 보입니다.

물론 사용자가 명시적으로 “이건 계획 먼저 세워줘”라고 요청해도 Plan Mode로 들어갈 수 있습니다.

## 디버깅 체크리스트

Plan Mode가 제대로 동작하지 않을 때, 아래 순서대로 확인해보세요.

### Plan Mode에 들어가야 하는데 안 들어갈 때

1. **작업이 Plan Mode에 적합한지 확인**
   - "README 오타 수정", "버튼 색상 변경" 같은 단순 작업은 Plan Mode에 들어가지 않습니다.
   - "인증 시스템 전체 교체", "데이터 파이프라인 새로 설계" 같은 큰 작업에서 주로 동작합니다.

2. **자동 Plan Mode가 비활성화되어 있는지 확인**
   - `config.toml`에 `[plan_mode] auto_enter = false`가 설정되어 있으면 자동 진입이 안 됩니다.

### Grok이 Plan Mode인데도 파일을 수정하려고 할 때

- Plan Mode가 제대로 활성화되지 않았을 수 있습니다.
- Grok이 "Plan Mode로 들어가도 될까요?"라고 물어봤는데 사용자가 승인하지 않았을 수 있습니다.
- `/status`나 TUI 상단에서 현재 모드가 Plan Mode인지 확인하세요.

### plan.md 파일이 생성되지 않을 때

- Plan Mode가 정상적으로 시작되었는지 확인하세요.
- 세션 디렉토리 (`~/.grok/sessions/...`)에 쓰기 권한이 있는지 확인하세요.
- 드물지만 디스크 공간 부족이나 권한 문제로 파일 생성이 실패할 수 있습니다.

### 계획을 승인했는데도 구현이 안 시작될 때

- Plan Mode가 종료된 후 “이제 구현해”라고 명시적으로 말해야 실제 구현이 시작됩니다.
- 단순히 “승인”만 하면 Plan Mode는 종료되지만, Grok은 사용자의 다음 지시를 기다립니다.

### 계획이 너무 장황하거나 실용적이지 않을 때

- "더 구체적으로", "파일 단위로 나눠서", "위험 요소 위주로" 같은 피드백을 주면 Grok이 더 실용적인 계획을 세우는 경우가 많습니다.
- 한 번에 너무 큰 범위의 작업을 요청하면 계획이 추상적으로 나올 수 있습니다.

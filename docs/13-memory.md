# 12-메모리

Grok Build는 기본적으로 **세션 단위**로 동작합니다.  
즉, 새로운 세션을 시작하면 이전 세션에서 했던 대화나 결정 사항을 전혀 기억하지 못합니다.

하지만 프로젝트를 오랫동안 작업하다 보면, “이전에 설명했던 규칙”, “지난번에 해결했던 버그 패턴”, “팀의 아키텍처 결정” 등을 매번 다시 설명하는 것이 매우 비효율적입니다.

이런 문제를 해결하기 위해 Grok Build가 제공하는 기능이 바로 **Memory**입니다.

---

## Memory란 무엇인가?

### Memory의 개념

**Memory**는 Grok이 여러 세션에 걸쳐 **중요한 정보**를 기억하고, 필요할 때 자동으로 불러올 수 있게 해주는 기능입니다.

Memory에 저장되는 정보의 예시:
- 프로젝트의 코딩 컨벤션
- 자주 사용되는 디버깅 방법
- 아키텍처 결정 사항
- 특정 파일이나 함수에 대한 설명
- 팀의 개발 규칙
- 이전에 해결했던 문제와 그 해결책

Memory가 활성화되어 있으면, Grok은 사용자가 질문할 때마다 자동으로 관련된 Memory를 검색해서 참고합니다.

### Memory vs AGENTS.md vs Skill

| 기능       | 지속 범위         | 활성화 방식         | 목적 |
|------------|-------------------|---------------------|------|
| **AGENTS.md** | 프로젝트 전체     | 항상 적용           | 프로젝트의 큰 방향과 규칙 |
| **Skill**     | 특정 작업/상황    | 필요할 때 호출      | 반복되는 작업 절차 |
| **Memory**    | 여러 세션에 걸쳐  | 자동 검색           | 장기 기억 (사실, 결정, 패턴) |

Memory는 **“한 번 알려주면 계속 기억하는”** 가장 편리한 방법입니다.

---

## Memory 활성화 방법

Memory는 기본적으로 **비활성화**되어 있습니다. (실험적 기능)

### 1. CLI 플래그로 활성화 (임시)

```bash
grok --experimental-memory
```

### 2. 환경 변수로 활성화 (권장)

```bash
export GROK_MEMORY=1
grok
```

이 방법은 터미널 세션 동안 Memory를 활성화합니다.

### 3. config.toml에서 영구 활성화 (가장 추천)

`~/.grok/config.toml`에 아래 내용을 추가하세요:

```toml
[memory]
enabled = true
max_memories = 200          # 저장할 수 있는 최대 Memory 개수
```

### Memory 강제 비활성화

Memory를 사용하고 싶지 않을 때는:

```bash
grok --no-memory
```

## Memory가 어떻게 동작하는가?

### Memory 저장 과정

Grok이 대화 중에 중요한 정보를 발견하면, 자동으로 Memory에 저장합니다.

예를 들어 사용자가 다음과 같이 말하면:

> “이 프로젝트에서는 커밋 메시지를 Conventional Commits 형식으로 작성해.”

Grok은 이 정보를 Memory에 저장합니다.

### Memory 검색 과정

이후에 사용자가 다음과 같이 물으면:

> “커밋 메시지 어떻게 작성해?”

Grok은 자동으로 Memory를 검색해서 이전에 저장된 “Conventional Commits” 규칙을 찾아서 참고합니다.

### Memory의 특징

- **자동 검색**: 사용자가 직접 Memory를 요청하지 않아도, Grok이 필요하다고 판단하면 자동으로 불러옵니다.
- **검색 가능**: `/memory search <키워드>` 명령어로 직접 Memory를 검색할 수 있습니다.
- **관리 가능**: `/memory list`, `/memory delete` 등으로 Memory를 직접 관리할 수 있습니다.

---

## 간단한 사용 예시

### 예시 1: 프로젝트 컨벤션 기억시키기

**첫 번째 세션**:
```
이 프로젝트는 TypeScript를 사용하고, any 타입은 최대한 피해. 
컴포넌트는 함수형으로만 작성하고, 상태 관리는 Zustand를 사용해.
```

Grok이 이 정보를 Memory에 저장합니다.

**다음 세션** (새로운 세션):
```
UserProfile 컴포넌트를 만들어줘.
```

Grok은 자동으로 Memory에서 “함수형 컴포넌트 + TypeScript + Zustand” 규칙을 찾아서 적용합니다.

### 예시 2: 디버깅 패턴 기억시키기

```
지난번에 이 에러는 prisma client가 초기화되지 않아서 발생했었어. 
이런 경우에는 npx prisma generate를 먼저 실행하는 게 좋아.
```

이후에 비슷한 에러가 발생하면 Grok이 자동으로 이 해결 방법을 제안합니다.

## Memory 관리 명령어

Memory는 `/memory` 명령어를 통해 직접 관리할 수 있습니다.

### `/memory list`

현재 저장된 Memory 목록을 보여줍니다.

```bash
/memory list
```

- 저장된 Memory의 제목과 간단한 내용, 저장 시점을 확인할 수 있습니다.

### `/memory search <키워드>`

키워드로 Memory를 검색합니다.

```bash
/memory search prisma
/memory search authentication
```

- Grok이 자동으로 검색하지 못한 Memory를 직접 찾아보고 싶을 때 유용합니다.

### `/memory delete <id>`

특정 Memory를 삭제합니다.

```bash
/memory delete 123
```

### `/memory clear`

모든 Memory를 삭제합니다.

**주의**: 이 명령어는 되돌릴 수 없으니 신중하게 사용하세요.

---

## Memory 저장 전략 (무엇을 저장하면 좋은가)

Memory는 자동으로 저장되기도 하지만, 사용자가 직접 중요한 정보를 Memory에 저장하는 것도 가능합니다.

### 저장하면 좋은 정보

**1. 프로젝트 컨벤션**
- “이 프로젝트는 Prettier + ESLint를 사용하고, airbnb 스타일을 따릅니다.”
- “함수형 컴포넌트만 사용하고, 클래스 컴포넌트는 금지합니다.”

**2. 디버깅 패턴**
- “Prisma 관련 에러가 발생하면 npx prisma generate를 먼저 실행해보기.”
- “TypeScript any 에러는 as unknown as Type으로 우회하는 경우가 많음.”

**3. 아키텍처 결정**
- “이 프로젝트의 상태 관리는 Zustand를 사용하고, store는 src/store/에 위치합니다.”
- “API 호출은 모두 src/api/ 폴더에 모아두었습니다.”

**4. 팀 규칙**
- “커밋 메시지는 Conventional Commits 형식을 따릅니다.”
- “PR을 올릴 때는 반드시 테스트 결과를 포함해야 합니다.”

**5. 자주 묻는 질문에 대한 답변**
- “이 에러의 원인은 보통 .env 파일이 로드되지 않아서입니다.”

### 저장하면 안 좋은 정보

- 너무 자주 바뀌는 정보 (예: 현재 진행 중인 작업 내용)
- 한 번만 사용하는 임시 정보
- 개인적인 메모 (Memory는 프로젝트 단위로 공유될 수 있음)

---

## Memory와 AGENTS.md, Skill의 함께 쓰는 방법

### AGENTS.md + Memory

- **AGENTS.md**: 프로젝트의 **큰 방향**과 **영구적인 규칙**을 담당
- **Memory**: 프로젝트를 진행하면서 **발견한 사실이나 패턴**을 저장

**예시**:
- AGENTS.md: “이 프로젝트는 TypeScript를 사용합니다.”
- Memory: “이전 세션에서 UserService.ts의 getUserById 함수가 null을 반환할 수 있다는 것을 발견함.”

### Skill + Memory

- **Skill**: 특정 작업을 **어떻게 수행할지**에 대한 절차를 정의
- **Memory**: 그 작업을 수행하면서 **발견한 팁이나 주의사항**을 저장

**예시**:
- Skill: `unit-test-generation` (테스트 작성 절차)
- Memory: “이 프로젝트에서는 MSW를 사용한 API 모킹을 선호합니다.”

이렇게 세 가지를 잘 조합하면, Grok이 프로젝트를 점점 더 잘 이해하고 도와줄 수 있습니다.

## Privacy와 보안 고려사항

### Memory에 저장되는 정보

Memory는 사용자가 명시적으로 지우지 않는 한, 계속 저장됩니다.

따라서 다음 정보는 Memory에 저장되지 않도록 주의해야 합니다:

- API 키, 비밀번호, 토큰 등 민감한 정보
- 고객 데이터나 개인정보
- 회사 내부의 비밀 프로젝트 내용

### Memory 삭제 방법

- `/memory delete <id>`: 특정 Memory 삭제
- `/memory clear`: 모든 Memory 삭제

중요한 프로젝트를 다룰 때는, 작업이 끝난 후 `/memory clear`를 하는 습관을 들이는 것도 좋습니다.

### Memory는 어디에 저장되나?

Memory는 `~/.grok/memory/` 폴더에 저장됩니다.

- Global Memory: 모든 프로젝트에서 공유
- Project Memory: 특정 프로젝트에만 적용 (추후 지원 예정)

현재는 대부분 Global Memory로 동작합니다.

## Memory 활성화 시 Grok의 동작 변화

Memory를 활성화하면 Grok의 행동에 다음과 같은 변화가 생깁니다.

### 1. 자동으로 관련 Memory 검색

사용자가 질문을 하면, Grok이 자동으로 Memory를 검색해서 관련된 정보를 찾아봅니다.

예:
- “이전에 설명했던 인증 방식이 뭐였지?”라고 물으면, Memory에 저장된 인증 관련 내용을 자동으로 불러와서 답변합니다.

### 2. 반복 질문 감소

같은 질문을 여러 번 하지 않아도 됩니다.

- “이 프로젝트의 상태 관리 방식이 뭐였더라?” 
- “지난번에 이 버그는 어떻게 해결했었지?”

이런 질문들이 줄어듭니다.

### 3. 프로젝트 이해도 향상

Grok이 프로젝트를 점점 더 잘 이해하게 됩니다.

- 초기에는 “이 프로젝트가 뭘 하는 건가요?”라고 물을 수 있지만,
- Memory가 쌓일수록 “이 프로젝트의 결제 모듈은 어떻게 되어 있나요?”처럼 구체적인 질문을 할 수 있게 됩니다.

### 4. 컨텍스트 효율성 증가

Memory가 중요한 정보를 대신 기억해주기 때문에, 매 세션마다 긴 설명을 반복하지 않아도 됩니다. 결과적으로 컨텍스트 창을 더 효율적으로 사용할 수 있습니다.

## Memory 사용 시 주의할 점과 한계

### Memory의 한계

**1. 실험적 기능**
- Memory는 아직 실험적(experimental) 기능입니다.
- 동작이 완벽하지 않을 수 있고, 예기치 않은 문제가 발생할 수 있습니다.

**2. 정확성 보장 없음**
- Grok이 Memory를 잘못 해석하거나, 오래된 정보를 그대로 사용할 수 있습니다.
- 중요한 정보는 Memory에만 의존하지 말고, AGENTS.md나 문서에도 함께 기록하는 것이 좋습니다.

**3. 컨텍스트 제한**
- Memory는 무한대로 저장되지 않습니다. (설정에서 `max_memories`로 제한 가능)
- 너무 많은 Memory가 쌓이면 검색 효율이 떨어질 수 있습니다.

**4. 프로젝트 간 격리 부족 (현재)**
- 현재 Memory는 대부분 Global Memory로 동작합니다.
- 여러 프로젝트를 동시에 진행할 경우, Memory가 섞일 수 있습니다.
- (추후 프로젝트별 Memory 격리 기능이 추가될 예정)

## Memory 관련 Best Practices

### 1. Memory는 “보조 기억장치”로 활용하라

Memory는 완벽한 기억을 보장하지 않습니다.  
중요한 결정이나 규칙은 **AGENTS.md**에도 함께 기록하는 것을 추천합니다.

### 2. Memory가 자동으로 저장하게 두되, 주기적으로 정리하라

- `/memory list`로 주기적으로 저장된 Memory를 확인하세요.
- 불필요하거나 잘못 저장된 Memory는 `/memory delete`로 정리하는 습관을 들이세요.

### 3. 중요한 정보는 명확하게 전달하라

Memory에 저장하고 싶은 내용이 있다면, 명확하고 구체적으로 말하는 것이 좋습니다.

**좋은 예**:
```
이 프로젝트에서는 인증 관련 로직은 src/auth/에 모아두고, JWT를 사용합니다.
```

**나쁜 예**:
```
인증은 적절히 해.
```

### 4. Memory + AGENTS.md + Skill 조합을 적극 활용하라

- **AGENTS.md**: 프로젝트의 큰 방향
- **Skill**: 반복 작업의 절차
- **Memory**: 발견한 사실과 패턴

이 세 가지를 잘 조합하면 Grok이 프로젝트를 매우 잘 이해하고 도와줄 수 있습니다.

### 5. 중요한 프로젝트에서는 Memory 사용을 신중하게

고객 데이터, 보안이 중요한 프로젝트, 또는 내부 비밀 프로젝트에서는 Memory 사용을 최소화하거나 사용하지 않는 것을 고려하세요.

## 배경 지식: 이 기능이 왜 이렇게 동작하는가

> **참고**: 이 섹션은 Grok 공식 문서에 명시된 설계 의도를 그대로 설명한 것이 아닙니다.  
> 실제 동작 방식과 관찰, 그리고 논리적 해석을 바탕으로 작성한 **참고용 설명**입니다.  
> xAI에서 공식적으로 발표한 설계 철학이 아니라는 점을 참고해 주세요.

Memory 시스템이 현재와 같은 형태로 제공되는 배경과 특징을 정리했습니다.

### 1. 왜 Memory가 세션과 독립적으로 동작하나?

Grok Build는 기본적으로 **세션 단위**로 동작합니다.  
하지만 프로젝트를 오래 하다 보면, “이전에 설명했던 규칙”이나 “해결했던 버그 패턴”을 매번 다시 알려주는 것이 매우 비효율적입니다.

그래서 Memory는 **세션과 별개로** 중요한 정보를 저장하고, 필요할 때 자동으로 불러오는 방식으로 동작합니다.  
이렇게 하면 사용자가 “이건 이전에 말했던 내용이야”라고 일일이 알려주지 않아도 Grok이 스스로 기억할 수 있습니다.

### 2. 왜 현재는 Global Memory로 동작하나?

현재 Memory는 대부분 **Global** (모든 프로젝트에서 공유)로 동작합니다.  
이는 구현의 복잡도와 사용 편의성을 고려한 초기 설계로 보입니다.

현재는 “여러 프로젝트에서 공통으로 기억해야 할 정보”를 저장하는 데 최적화되어 있으며, 프로젝트별로 Memory를 격리하는 기능은 아직 제공되지 않습니다.

### 3. 왜 AGENTS.md, Skill, Memory를 구분해서 쓰나?

- **AGENTS.md**: 프로젝트의 **영구적인 큰 방향**과 철학
- **Skill**: 특정 **작업의 절차**와 패턴
- **Memory**: 프로젝트를 하면서 **발견한 사실**이나 경험을 축적

이 세 가지는 목적과 지속 기간이 다르기 때문에, 섞어서 사용하면 오히려 혼란스러워질 수 있습니다.

## 디버깅 체크리스트

Memory가 제대로 동작하지 않을 때, 아래 순서대로 확인해보세요.

### Memory가 저장되지 않을 때

1. **Memory가 활성화되어 있는지 확인**
   ```toml
   [memory]
   enabled = true
   ```
   또는 환경 변수 `GROK_MEMORY=1`이 설정되어 있는지 확인하세요.

2. **중요한 정보를 명확하게 전달했는지 확인**
   - Memory는 자동으로 중요한 정보만 저장하려고 합니다.
   - 너무 모호하게 말하면 (“적절히 해”, “좋은 코드로 만들어”) 저장되지 않을 수 있습니다.
   - 구체적으로 말하는 것이 중요합니다.

### Memory가 자동으로 불러와지지 않을 때

1. **키워드가 너무 구체적이거나 모호한지 확인**
   - Memory 검색은 키워드 기반입니다.
   - 너무 긴 문장보다는 핵심 키워드(“JWT”, “Zustand”, “인증 로직”)를 사용하는 것이 더 잘 작동합니다.

2. **Memory가 너무 많이 쌓여서 검색 효율이 떨어졌을 수 있음**
   - `/memory list`로 불필요한 Memory가 많이 쌓여있지 않은지 확인하세요.
   - 주기적으로 정리하는 것이 좋습니다.

### Memory가 이상한 내용을 불러올 때

1. **오래된 정보가 남아있을 수 있음**
   - 프로젝트 구조가 바뀌었는데, 이전에 저장된 Memory가 그대로 남아있을 수 있습니다.
   - `/memory list`로 확인하고 필요하면 삭제하세요.

2. **비슷한 내용이 여러 개 저장되어 있을 수 있음**
   - 비슷한 내용이 중복 저장되면 Grok이 어떤 것을 우선할지 헷갈릴 수 있습니다.
   - 중복되는 Memory는 정리하는 것이 좋습니다.

---

이 두 섹션은 Memory를 더 깊이 이해하고, 문제가 생겼을 때 스스로 해결할 수 있도록 돕기 위해 추가되었습니다.


## 전체 가이드 마무리

`12-메모리.md`를 모두 읽었다면, 이제 Grok Build의 **장기 기억** 기능을 이해한 것입니다.

### 핵심 요약

- Memory는 **여러 세션에 걸쳐** 중요한 정보를 기억하게 해주는 기능입니다.
- 활성화 방법은 CLI, 환경변수, config.toml이 있습니다.
- `/memory` 명령어로 직접 관리할 수 있습니다.
- AGENTS.md, Skill과 함께 사용하면 훨씬 강력해집니다.
- 보안이 중요한 프로젝트에서는 신중하게 사용해야 합니다.

### Memory를 언제부터 도입하면 좋을까?

- 프로젝트가 어느 정도 진행되어서 **반복되는 패턴**이 보이기 시작할 때
- **중요한 결정**을 여러 번 설명하게 될 때
- 팀원들이 늘어나서 **같은 설명을 반복**하게 될 때

초기에는 Memory 없이 시작했다가, 필요성을 느낄 때 활성화하는 것이 가장 자연스럽습니다.
